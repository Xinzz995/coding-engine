# Technical Alignment（技术对齐）

业务口径确定后（scenario-alignment 对齐稿或本就清晰的需求），把本功能**改起来贵**的技术决策整理成一份可快速拍板的技术对齐稿。此 skill 只对齐「合同」：数据怎么落、边界怎么开、状态怎么转、权限在哪判、旧数据怎么办——不写实现步骤、不拆任务、不改代码。

核心目标：**让人只拍板少数贵决策，中间「怎么写代码」交给自动化流水线；合同写成后续验收标准可直接引用的陈述。**

## 何时使用（可选前置，不是必经步骤）

功能触碰以下任何一项时使用：

- 新增/变更持久化结构（表、字段、文件格式）或需要处理存量数据
- 新增/变更对外接口（HTTP API、CLI 参数与退出码契约、暴露的文件产物）
- 引入新状态机或改变现有状态流转
- 权限/可见性的判定模型变化
- 引入外部服务或新依赖

**不需要用它的情况**：纯 UI 调整、文案/命名变更、无持久化与边界变化的小功能——直接用 prd-generate 创建 PRD。

## 合同判定三问（什么进合同）

对每个候选技术决策问三问，**任一为是**才进合同：

1. 影响存量数据吗？（迁移、兼容、不可物理删除类约束）
2. 被多方依赖或公开后难收回吗？（对外接口、文件格式、CLI 契约）
3. 错了要连锅端重做吗？（状态机、权限模型、核心数据结构）

三问全否的决策（函数怎么拆、内部结构、代码组织、任务顺序）不进合同——留给实现者按项目约束自行决定，不要替它做。

## 输入

- 业务口径：scenario-alignment 对齐稿（`docs/prds/align-*.md`）或用户的清晰需求
- 当前仓库的项目文档（AGENTS.md 索引的架构/约定文档）与相关代码事实
- 可选：现有 schema、接口定义、相关旧 PRD

## 工作流程

1. 读取项目约束：
   - 先读根级 `AGENTS.md`（注意其中的硬约束——它们常常直接决定合同条款）
   - 按 `AGENTS.md` 的文档索引读取相关架构/codebase 文档
2. 读取业务输入，列出全部业务动作（生成、发布、下载、编辑……）与角色。
3. 查证现有技术事实，只保留会影响合同的：
   - 现有的表/存储结构、接口、状态字段、权限判定位置
   - 目标行为与现状的结构性差异（如「现在是覆盖存储，目标要历史保留」）
   - 不能破坏的既有契约（已公开的接口、已有数据）
4. 沿数据流把每个业务动作走一遍：它读什么、写什么、状态怎么变、权限在哪判——把落点整理成合同条目，逐条过「判定三问」。
5. 每条合同写成可验证陈述并附一句理由；存在多个合理方案且选择会改变合同的，进「需要拍板的问题」（最多 1-3 个，必附推荐）。
6. 单列「不可逆项」清单；输出技术对齐稿。如果拍板问题会阻塞合同成立，先只问问题，不强行生成。

## 提问规则

- 最多 3 个；超过 3 个时先问最上游的 1-3 个（答案会改变其他合同条目的优先）。
- 每个问题必须附「推荐：...」及一句理由。
- 不问能通过代码、文档或用户已给材料判断的问题。
- 不问实现细节（函数拆分、内部命名、任务顺序）；只问会改变合同的选择（如「历史版本按次全量存储还是存差异？推荐：全量，报告体量小且读取简单」）。

## 输出格式

```markdown
---
title: "技术对齐稿: [功能名]"
status: active
updated: YYYY-MM-DD（当天日期）
scope: root 或子项目名
---

# [功能名] 技术对齐稿

## 概述
- [一句话：本功能的技术承接方式；注明业务输入来源（对齐稿路径或需求）]

## 数据与持久化
- [新增/变更的结构：表/集合/文件、字段与类型与默认值；存量数据的处理；没有则写「无变化」]

## 接口与边界
- [新增/变更的对外接口、CLI 契约、文件产物；依赖的外部服务；没有则写「无变化」]

## 状态与流转
- [状态列表、初始状态、谁能触发哪个迁移；没有则写「无」]

## 权限承接
- [判定发生在哪一层、依据什么；各角色能做什么；没有变化则写「无变化」]

## 兼容与迁移
- [旧数据/旧行为如何过渡、升级路径；无需迁移时写明理由]

## 不可逆项
- [公开后难收回的决策，每项一行：数据迁移 / 对外接口 / 新外部依赖；没有则写「无」]

## 需要拍板的问题
1. ...
   推荐：...
```

## 输出压缩规则

- 每条合同是**可验证陈述**：写「报告记录只追加、永不覆盖」，不写「数据要安全可靠」；写「导出权限在服务端判定」，不写「注意权限安全」。后续 PRD 的 acceptance criteria 应能逐条引用。
- 允许 schema 级描述（字段/类型/默认值、接口入参出参语义、状态流转），**禁止实现代码、伪代码、函数签名、组件结构**。
- 每条合同附一句理由（为什么这么定），不展开长篇论证；与现状的差异一笔带过（「现为 X，改为 Y」）。
- 各节没有内容时写「无」或「无变化」，不留空、不硬凑。
- 不复述业务对齐稿内容，只写技术承接；业务口径冲突时回到第一端解决，不在合同里改口径。
- 只有会改变合同的选择才进「需要拍板的问题」，最多 3 个；没有就写「无」。

## 禁止内容

- 不写实现步骤、任务拆分、开发顺序、user stories。
- 不写实现代码、伪代码、函数签名、组件/模块内部结构。
- 不替业务口径做主：业务规则有歧义时指回 scenario-alignment，不自行裁决。
- 不把三问全否的实现细节写进合同。

## 保存与下一步（转换闭环）

- 用户确认（或要求保存）后，保存到 `docs/prds/tech-<feature-name>.md`（kebab-case；目录不存在则创建）。monorepo 归属规则与 PRD 一致：功能只涉及一个子项目 → `<子项目>/docs/prds/`；跨子项目或单项目 → 根 `docs/prds/`。
- 「需要拍板的问题」经用户拍板后，把确认结果合并进对应合同条目再保存；未拍板的问题不得擅自按推荐答案落盘。
- **技术对齐稿是 prd-generate 的一次性输入材料，不是持续维护的真相源**：用户要继续时，把业务对齐稿（如有）与本合同稿一起交给 prd-generate（对它说「基于 docs/prds/align-xxx.md 和 docs/prds/tech-xxx.md 创建 prd」）；正式 PRD 生成后，将合同稿 frontmatter 的 `status` 置为 `superseded`。此后需求变更直接改正式 PRD；长期技术事实的沉淀由 /compound-docs 负责进架构文档，不回改合同稿。
