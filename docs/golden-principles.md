# 黄金原则

以下五条原则裁决新功能是否值得做、何时算完成、什么结果可以相信。每个新功能在写代码前，必须在实现计划或 PRD 中逐条留下「适用性、设计裁决、验证证据」；不适用要写理由，不能省略。语言、目录、构建、版本等仓库实现约束由根 `AGENTS.md` 的「硬约束」单一维护，本文不重复。

## 1. 先定义可证伪的完成合同，再开始实现

- **规则**：每条需求都必须落成可观察的 acceptanceCriteria，并逐条绑定验证命令、测试断言或人工验收证据；「保证没有错误」「体验良好」「按方案完成」不能单独充当完成条件。无法自动判定的意图必须显式标为人工裁决，不得伪装成自动通过。
- **为什么**：持续执行只能解决「不停」，不能解决「方向正确」；模糊目标会让生成方自行选择最容易满足的代理指标。
- **怎么检查**：计划或 PRD 中存在 `acceptanceCriteria → 验证方式/证据` 对照；每条标准都能回答通过与失败分别会观察到什么；全文不存在无配套判据的绝对化完成承诺。

## 2. 生成方不得给自己签发通过，证据必须标明信任级别

- **规则**：Agent 的完成自述、`passes=true` 和 agent 可写区记录都只能视为候选声明；最终通过至少需要一道不依赖该自述的机械门禁或独立验证。新增或修改验收链路时，验证目标必须由引擎显式绑定到当前 story 与当前产物，不能靠自由文本猜测；agent 声明不得包装成防伪事实。
- **为什么**：角色名称不同不等于信任边界不同，同一模型、同一可写工作区和同一错误代理会产生共谋假绿。
- **怎么检查**：测试或 dogfood 注入「生成方声称成功但门禁失败」场景，系统必须 fail-closed 且不得签发凭证；验收链路测试能证明验证的是指定 story/产物；报告与 schema 明确区分 engine/CI 机械事实和 agent 声明。

## 3. 自治范围每扩大一步，防线与可逆性必须同步增加一步

- **规则**：新增会扩大 Agent 写入、命令执行、并行、合并、部署或删除范围的能力时，同一变更必须给出与风险匹配的权限边界、超时与有界重试、隔离或回滚路径；合并、部署、删除数据等不可逆动作默认需要显式人工批准。
- **为什么**：更强的执行能力同时放大吞吐与错误爆炸半径；权限绕过和长时间运行不是安全保证。
- **怎么检查**：计划含「新增自治能力 → 失败场景 → 机械防线 → 恢复/审批」对照；自动化测试覆盖超时、中断、重试耗尽和回滚/拒绝审批路径；不扩大自治范围时写明不适用理由。

## 4. 原生执行能力优先复用，核心差异只建在控制平面

- **规则**：实现循环续跑、subagent、worktree、memory、hooks 等能力前，必须核对 Claude Code、Codex、Cursor 当前原生能力，优先做适配而非复制。项目核心合同保持 runner-neutral；供应商参数和行为差异收口在 adapter，只有存在可度量的原生缺口时才自建执行能力。
- **为什么**：Agent 执行能力会持续商品化；可移植的验收政策、状态语义和证据合同才不会随单一工具升级而失去价值。
- **怎么检查**：计划含「原生能力对照与 build/adapt 裁决」，写明缺口、选择和衡量指标；新增供应商特有逻辑不进入 runner-neutral 核心类型/状态合同，确需进入时必须有 ADR 说明不可避免的耦合。

## 5. 以假绿率和失败恢复衡量价值，每个真实失败都必须固化为回归

- **规则**：新增或修改运行时行为时，先写至少一个失败路径，再写成功路径；dogfood、线上或审查发现的真实缺陷必须沉淀为可复现 fixture/回归测试，无法自动化时登记明确的人工回归断言和原因。涉及 Agent 调用的新增路径至少记录实际路由、结局与耗时，runner 能提供时同时记录 token/成本。
- **为什么**：运行更久、调用更多模型或最终显示绿色都不证明更可靠；项目真正需要持续降低的是 false-green、不可恢复中断和人工复核成本。
- **怎么检查**：行为变更的测试清单同时含成功与失败断言；每条 finding 都能追溯到测试/fixture 或显式待办裁决；计划写明预期影响的指标（假绿、恢复、人工介入、耗时/成本中至少一项），验收时对账而不是只报告「已完成」。
