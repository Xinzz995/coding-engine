# Issue #207: 干净检出外部链接核对的 30 秒统一期限在冷缓存机器上偏紧

## Goals

修复干净验证检出在冷缓存或高负载机器上核对外部普通文件链接时，固定 30 秒期限与实际工作量无关的问题。使用内部、单调、有上限的自适应预算，让可完成的 1 GiB 以内核对不再因统一短期限被迫整轮重跑，同时保留所有身份核对和失败关闭语义。

当前事实：`src/engine/clean-validation-checkout.ts` 仍固定使用 `EXTERNAL_LINK_SNAPSHOT_DEADLINE_MS = 30_000`；一次核对最多接受 1024 条链接、单文件 256 MiB、去重后实际目标读取量 1 GiB。0.35.0 RC5 曾在约 25 分钟全量测试后的 macOS 冷缓存现场因此失败，下一轮热缓存通过。该现场证明“30 秒可能偏紧”，但不把缓存置换直接当成已经证明的唯一根因。

## Non-Goals

- 不增加用户可配置的链接核对超时，不把安全预算交给每个项目调参。
- 不提高链接数量、单文件大小或 1 GiB 去重读取量上限。
- 不跳过链接内容摘要、路径解析、文件系统类型、挂载、hard link、前后身份或开发工作树回链检查。
- 不为超时结果降级、重试后放行或复用不完整快照；证据不足仍然失败关闭。
- 不改 Windows 原生路径检查器、Validator 语义、Agent 超时、自动轮询、队列或更多 Agent 编排。
- 不用真实等待数分钟的脆弱测试代替确定性时钟和慢 I/O 注入。

## Risk

主要风险是扩大预算后让真正卡死的读取更晚失败，或为了提前计算工作量引入新的检查竞态。180 秒硬上限把新增最坏等待控制在 150 秒以内，仍显著小于一次二十多分钟整轮重跑；元数据与内容身份必须在同一受管边界内前后复核，不能用预扫结果直接放行。任何无法建立工作量、进度或最终身份的情况继续按 `topology-unverifiable` 失败关闭。

#### Acceptance Criteria

- [ ] 生产预算使用唯一固定公式：`budgetMs = min(180000, 30000 + linkCount * 20 + ceil(distinctTargetBytes / 8388608) * 1000)`。`linkCount` 统计每条链接；`distinctTargetBytes` 只按稳定去重后的外部普通文件目标计一次。预算使用单调时钟，并从一次核对开始到全部读取及最终复核共用同一个绝对期限，不能给每个文件重新计时。
- [ ] 工作量必须由受管核对路径机械建立，并继续受现有 1024 条链接、单文件 256 MiB、总读取量 1 GiB 上限约束。若采用元数据预扫，内容读取前后必须重新核对同一链接与目标身份；元数据漂移、重复目标大小或摘要冲突继续失败关闭。
- [ ] 受管 reader、父进程监督期限和预算对象必须一致接受同一个自适应上限；任何外层固定期限都不能比已计算预算更短。中断、输出故障、进程未结算或监督证据不足仍按现有规则失败，不得被解释为普通预算超时。
- [ ] 超时错误必须提供有界、无路径泄露的进度诊断，至少包括：`budgetMs`、`elapsedMs`、`links`、`distinctTargets`、`completedLinks`、`completedTargets`、`readBytes`、`remainingBytes`。数字来自引擎或受管 reader 的机械观察；缺失值要明确标为不可得，不能猜测。
- [ ] 确定性单元测试覆盖公式边界：零工作量、重复目标只计一次字节、1024 条链接与 1 GiB 得到 178480 ms、非法或超上限输入拒绝、180 秒硬上限永不突破。
- [ ] 慢 I/O 回归在受控时钟/reader 下证明：超过旧 30 秒但小于自适应预算的合法读取能够完成；达到自适应期限会在有界时间失败并包含进度；AbortSignal、目标替换、等长改写、链接回开发树、特殊或远程文件系统继续失败关闭。
- [ ] 既有外部链接、干净检出、hard link、挂载、进程监督与跨平台回归全部通过；格式、静态检查、类型检查、构建、仓库健康、依赖审计和完整测试全部通过，测试前后不得新增 `coding-x-*` 临时残留。
