# Prompt 编写原则

## 根本判据：可预测性

一份 prompt 的好坏只看一条：agent 每次跑**同样的过程**（不是产出同样的结果）。token 成本、可维护性都是它的症状。下面每条原则都是这条的杠杆。

## 原则

### 1. no-op 检验——不改变行为的行删掉

逐句问：**这行指令改变模型的默认行为吗？** 模型本来就会做的事（「要仔细」「保持代码整洁」），写了等于付 token 和注意力买零。检验是相对模型的，不是相对读者的：争论一行是不是 no-op，用跑的结果裁决，不靠辩论。弱化词升级也是同一检验：「be thorough」不改行为就换更强的词，而不是加更多句子。

### 2. 完成判据：可判定，且要求量足

每个步骤的完成条件有两个独立性质：

- **可判定**——agent 能分清「做完/没做完」。模糊判据（「理解到位后继续」）让 agent 可以随时宣布完成，是提前收工的根源。
- **要求量**——判据要求做多少功课。「每条 acceptanceCriteria 都找到对应断言」迫使逐条核对；「检查测试覆盖」不迫使任何事。

**实证案例（0.12.1）**：builder 浏览器验收原来写「如果有 agent-browser 就用浏览器验证」——条件句把「有没有」留给模型自由裁量，4 个 story 自判无工具、静默降级为 HTTP 冒烟。改成「先跑 `which agent-browser` 探测」后消除：探测命令是二值可观察状态，没有裁量空间。**把条件句改写成探测/核对指令，是本仓库修 prompt 的第一招。**

### 3. 锚定词——用模型已有的概念，一个词顶一段话

预训练里已存在的概念词（红/绿、接缝、真相源、收口）自带完整语义，在 prompt 里反复出现同一个**词**（不是反复解释含义），行为就被它锚住。自造词要付出定义成本才能生效——所以先找现成的词；项目自有术语以 `docs/glossary.md` 为准，prompt、文档、代码命名共用一套词，触发和执行都更稳。

### 4. 信息分层——步骤在顶，参考下沉

顶层只放「按序做什么」，每步以完成判据收尾；定义、格式模板、边界规则作为参考材料放后段或引用文件。判断某段该不该下沉到引用文件：**所有执行路径都需要的内联，只有部分分支需要的下沉**。下沉材料靠指针措辞被触达——指针写得弱，材料等于不存在；先磨指针措辞，磨不动才收回内联。

### 5. 单一真相源——同一含义只写一处

一个规则在 prompt 内出现两处，改一漏一是时间问题；重复还会虚增该规则的显著性。仓库级的「唯一源」硬约束（skills/commands 不复制）在单份 prompt 内部同样成立。跨 prompt 的共享含义（如验收判据）指向同一处表述（glossary、golden-principles），不各写一版。

### 6. 防淤积——修订时逐句重跑 no-op 检验

加一行感觉安全、删一行感觉冒险，所以 prompt 只增不减是默认宿命。每次修订顺手做：本次触碰的章节逐句跑 no-op 检验，失败的整句删除（不是缩写）。全文件审计不必每次做，但 300 行以上的 prompt 是重点嫌疑对象。

### 7. 校准控制——按脆弱性分配规定性

同一份 prompt 不是每段都该写得一样死。**过程分叉会破坏可预测性的地方写死**：精确命令、探测指令、「不得增删 flag」（0.12.1 条件句改探测式即此类，见原则 2）。**分叉不影响过程等价的地方给方向并解释原因**：「做 X，因为 Y 会导致 Z」比死规则更稳——理解目的的 agent 能举一反三，堆死参数则把它退化成模板填充器。

多方案可行时给**默认值 + 例外逃生舱**（「用 X；遇到 Y 情形改用 Z」），禁止「可以用 A、B 或 C」的等权列举——等权菜单与条件句同病：把选择留给运行时裁量，每次跑的过程就不一样。

## 修订纪律

- 改 prompt 像改代码：说不出「这次改动改变了什么行为」的变更不提交。
- 引擎指令（builder.md / validator.md）的行为级变更，须有引擎真实跑 fixture 的 dogfood 实证或明确的失败案例驱动（如 0.12.1），不做凭感觉的措辞美化。
- skill 的 frontmatter `description` 是常驻上下文的成本，同时是触发器：触发词前置、一个触发分支写一次、身份描述不重复正文；功能相邻的 skill 在 description 写清各自阶段边界防触发抢活，正文配分流句（先例：scenario-alignment ↔ technical-alignment 以口径未定/已定分界）。
