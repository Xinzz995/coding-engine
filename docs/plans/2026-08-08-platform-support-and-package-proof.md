# 平台支持与候选安装证明

## 目标

把三类容易混淆的事实拆开并机械验证：

1. coding-x 自身支持 Linux、macOS、Windows；
2. 每个目标项目只选择自己真正需要验证的平台；
3. CI 的通用检查和发布可以继续运行在 Ubuntu。

同时补上现有发布链的缺口：Ubuntu 构建出的同一个候选 tarball，必须在三系统通过真实 npm 安装和命令
入口启动，之后才允许进入 npm staging。

## 非目标

- 不删除任一现有平台实现或真机测试；
- 不要求所有下游项目都运行三系统矩阵；
- 不承诺所有 Linux 发行版、macOS/Windows 版本或 CPU 架构；
- 不把模型、项目秘密或发布权限带入安装冒烟任务；
- 不改变 staged publishing、2FA、provenance 和三仓 Dogfood 的既有职责。

## 可证伪完成合同

| 编号 | 完成条件                                       | 通过证据                                                                              | 失败观察                                                      |
| ---- | ---------------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| AC-1 | npm 明确只接受三类受支持系统                   | 包元数据只列 `darwin/linux/win32`；未列 CPU 限制                                      | 未知系统仍被声明支持，或误拒绝已支持系统                      |
| AC-2 | 新项目的平台来自明确选择                       | init 展示已跟踪 workflow 提示并要求输入；`--yes` 无契约时停止                         | 无证据时自动生成三平台，或把 Ubuntu 控制任务当部署事实        |
| AC-3 | 契约能区分必需平台与额外 CI job                | `requiredPlatforms` 非空、唯一、均有对应 job；额外平台 job 合法                       | 必需平台无 job 仍通过，或额外 Ubuntu job 被误判非法           |
| AC-4 | coding-engine 对最低 Node 版本的三系统证据完整 | Linux、macOS、Windows 都有 Node 22；三者也有 Node 24；Windows 原生证明保留            | macOS 只测 Node 24，或新增任务未进入总闸                      |
| AC-5 | 候选只构建一次                                 | build job 产生一个 tarball、摘要和提交绑定；所有安装任务下载同一 artifact             | 每个平台重新打包，或只比较文件名不比较摘要                    |
| AC-6 | 同一候选在三系统真实安装并启动                 | Ubuntu 24.04、macOS 26、Windows 2022 在全新目录 npm 安装；真实 bin 入口 `--help` 成功 | 直接运行源码、复用项目 node_modules，或 Windows `.cmd` 未经过 |
| AC-7 | 安装证明是 staging 的机械前置                  | 候选总闸对失败/取消/超时/跳过 fail-closed；stage 只接受该 run 为 success              | 单个安装任务失败后候选仍可 stage                              |
| AC-8 | 文档不夸大证明范围                             | README 分开列产品系统族、自动验证参考环境、Node 版本与未覆盖架构                      | 把 CI 宿主写成部署要求，或把一个参考环境写成所有版本均已验证  |

## 实施步骤

1. 冻结 ADR、设计规格、支持表和本计划；明确兼容、版本与发布边界。
2. 扩展质量契约及解析：新增可选 `requiredPlatforms`，旧 v2 只读派生；新增平台覆盖校验和读取 helper。
3. 修改自动发现与 init：扫描明确 runner 仅作提示；要求用户输入平台；所生成的检查、准备和 jobs 仅覆盖
   已选择平台；没有适用本地检查时失败，不能以零项通过。
4. 更新 coding-engine 契约：增加 macOS Node 22，并从同一契约重新生成质量工作流；功能 PR 仍固定已
   发布的 0.34.1 裁判且通过 jobs 只读派生三平台，不能提前写入新字段。
5. 为候选安装增加独立跨平台 smoke 脚本和测试；更新 build-candidate 工作流为单次打包、三系统安装、
   fail-closed 汇总。stage 继续通过候选 run 的成功状态继承该证明。
6. 先固定候选、暂存、发布和 CodeQL 的 runner；受 0.34.1 管理的质量/政策流程暂保留旧 runner 字节，
   0.35.0 发布后的独立 Policy PR 再把它们固定到 Ubuntu 24.04 与 macOS 26。Windows 继续固定 2022。
7. 同步 0.35.0 minor 版本、README、架构、发布手册和跨项目质量规格。
8. 运行定向测试、格式、lint、typecheck、全量测试、构建、repository health 和成品 CLI 冒烟。
9. 通过受保护 PR 获取 exact-head 的七项源码平台总闸、CodeQL 和政策检查；再人工触发候选工作流，回读
   三系统安装任务、总闸、artifact 摘要和 stage 拒绝/接受边界。
10. 完成 0.35.0 Dogfood、staging、2FA 批准、稳定发布与 main 首次全绿后，使用独立 Policy PR 把
    coding-engine 固定裁判和显式 `requiredPlatforms` 一起更新到 0.35.0；该 PR 不能与候选功能合并。

## 兼容与恢复

- 旧 v2 契约没有 `requiredPlatforms` 时只从 jobs 派生；源字节和摘要保持不变。
- 新下游契约固定新 minor 版本，旧 coding-x 不会被声称兼容新字段；coding-engine 自举在 0.35.0 发布
  前保留旧裁判和缺省字段，发布后由独立 Policy PR 原子切换。
- 安装 smoke 不写仓库、没有 OIDC/npm 发布权限，只消费当前候选 artifact；失败后重新修复并构建新候选。
- 完成发布后，runner 固定版本若被 GitHub 下线，工作流必须显式升级并重新取得三系统证据，不能静默
  回到 `latest`；发布前的两个旧裁判托管流程是一次有测试锁定的自举例外。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用**。AC-1 至 AC-8 都有通过证据和明确失败观察。
- **验证**。本地单测、exact-head Quality Gate 和人工候选工作流三层缺一不可。

### 2. 生成方不得给自己签发通过

- **适用**。Ubuntu build 只能产生候选，不能替 macOS/Windows 签名。
- **验证**。三台独立 hosted runner 从 artifact 服务取得同一摘要，候选总闸只读取它们的真实结局。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用**。init 新增平台建议，但不能自动采用建议；候选多启动三台只读安装机器。
- **验证**。用户确认发生在任何写入前；安装任务无发布权限，失败只废弃候选，不修改 npm。

### 4. 原生执行优先，差异只在控制平面

- **适用**。各系统使用系统自带 npm 命令入口和 GitHub 原生 runner，不引入容器模拟系统。
- **验证**。Windows 必须经过 `.cmd`，Unix 必须经过 npm 创建的 bin；同一跨平台脚本只协调、不伪造结果。

### 5. 以假绿率和失败恢复衡量价值

- **适用**。目标是消除“源码在三系统绿，但发布包命令入口损坏仍可 stage”的假绿。
- **验证**。失败、取消、超时、跳过都阻断；记录精确候选 run、head 和 SHA，修复后必须新建候选。
