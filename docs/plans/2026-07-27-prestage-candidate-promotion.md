# npm 暂存前候选验证与精确提升

## 背景与问题

0.33.0 的真实候选验证连续在 npm stage 之后发现产品问题。旧 stage 因为绑定不可变压缩包，
不能吸收后续修复，只能拒绝后重建。失败关闭是正确的，但当前流程把“供 Dogfood 的候选包”
和“等待 2FA 批准的 npm stage”创建在同一次运行中，导致本可在 npm 之外发现的问题反复制造
待拒绝 stage。

本变更不降低三仓 Dogfood、人工发布批准或精确制品绑定。它只把顺序改为：先构建固定候选，
用该候选完成批准前验证，再由维护者显式选择该候选进入 npm staging。

## 完成合同

| 验收标准 | 失败信号 | 验证证据 |
|---|---|---|
| 候选构建不会取得 npm 发布身份 | 构建工作流出现 `id-token: write`、npm environment 或 `npm stage publish` | 工作流回归测试与真实 Actions 权限摘要 |
| npm staging 只能消费成功的当前 `main` 候选 | 来源不是指定构建工作流、运行未成功、提交已落后或证据身份不一致仍能继续 | 证据脚本失败测试、工作流来源/提交核验 |
| 人工不需要逐文件核对 | staging 要求手工输入多个文件摘要或逐文件确认 | 只输入版本与候选运行编号；工作流自动读取并核对压缩包摘要 |
| npm 接收的内容等于 Dogfood 使用的候选 | 候选摘要与 npm 返回的 SHA-1/SHA-512 不同仍生成 staged 证据 | `record-stage` 不一致回归测试 |
| 稳定发布能追溯构建运行和暂存运行 | 标签只能找到 stage，不能找到原候选，或任一运行身份可被替换 | 发布工作流分别回读两次运行并下载原候选 |
| 旧 schema 证据不能混入新流程 | schema v1 候选被新 staging 或发布流程接受 | schema 版本失败测试 |

## 设计裁决

1. 新增 `build-candidate.yml`，只负责检查、构建、打包和保存候选；它没有 OIDC 与 npm
   environment。
2. 保留 `stage-candidate.yml` 文件名，避免改变 npm Trusted Publisher 身份；它改为接收候选
   运行编号和版本，先回读 GitHub 运行事实，再下载并核对原候选。
3. staging 前要求候选提交仍是当前远端 `main`。若其后合并了任何提交，停止并重新构建、
   Dogfood，避免维护者凭主观判断忽略可能影响发布物的变化。
4. 发布证据 schema 升为 v2，分别记录候选构建运行和 npm staging 运行。annotated tag 继续只
   固定 stage run、stage ID 和候选 SHA-256；发布工作流从不可变 stage 证据解析原候选运行，
   并分别回读两次成功运行。
5. 摘要核对全部自动完成。维护者只选择候选运行，不逐文件签名，也不手工复制 SHA-256。

## 黄金原则对照

| 原则 | 适用性与裁决 | 验证 |
|---|---|---|
| 1. 可证伪完成合同 | 适用。上表逐条给出可观察失败信号，不以“候选已构建”代替可发布。 | 脚本单测、工作流文本回归、真实候选运行 |
| 2. 不得自签 | 适用。构建任务只能生成候选声明；三仓 Dogfood 与独立 staging 才能推进发布。 | 构建任务无 OIDC；stage 回读成功运行与精确提交 |
| 3. 自治与风险对称 | 适用。只有 stage 工作流拥有短期 OIDC，仍需手动触发和最终 2FA 批准。 | 权限断言、错误来源/旧提交失败测试 |
| 4. 原生能力优先 | 适用。复用 GitHub artifact、运行 API、npm stage 与摘要，不新建服务或数据库。 | 架构和依赖不增加常驻组件 |
| 5. 失败恢复 | 适用。先固化旧 schema、错运行、旧提交、摘要不一致等失败路径；候选失败不再产生 npm stage。 | 回归测试与一次真实失败演练 |

## 明确不做

- 不自动批准、拒绝或公开 npm stage；
- 不因候选构建成功而跳过 coding-engine、Go、Python Dogfood；
- 不为每个包内文件单独生成需要人工处理的摘要；
- 不迁移或批准已有的 v1 stage，它们按旧候选处理；
- 不改变 `latest`、标签和不可变 GitHub Release 的人工收口顺序。
