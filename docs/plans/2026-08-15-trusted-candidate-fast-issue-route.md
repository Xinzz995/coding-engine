# 候选身份闭环、全量检查复用与 Issue 最小入口

## 目标与边界

本轮把交付路线收缩为三个可以机器判定的闭环：候选包身份、同输入检查复用、单 Issue 到单 PR。
先修复测试制造的系统临时目录残留，再以「Issue 被标记 ready 到 PR 得到可信结论的总时间」作为首要
效率指标。

本轮不做自动轮询、多任务队列、GitLab/Qoder 全覆盖、更多 Agent 编排、自动合并或自动发布。
`issue run` 是维护者显式启动或继续一次运行的入口；CI 尚未结束时写回状态并停止，由同一命令继续，
不在后台等待。npm staging 仍由受保护环境和人工批准触发，但批准前必须由机器读入三仓结果。

## 设计裁决

### 候选身份与三仓证明

1. `packed.json` 升级后记录两层身份：不可变 tarball SHA-256，以及 npm 安装后应出现的全部包文件
   路径、大小和内容摘要。候选 CLI 接受显式 `--candidate-evidence`，从自己的真实包根逐文件核对；
   证据文件本身不在包内，避免 tarball 摘要自引用。
2. 候选身份摘要只覆盖规范化、可复核字段：包名、版本、来源提交、candidate workflow run、tarball
   SHA-256 和运行文件树摘要。`--shadow` 没有候选证据仍可用于普通本地试验，但不得生成可供发布使用
   的 Dogfood 证明。
3. 成功的候选 Shadow 运行由引擎在 workspace 写出 `candidate-proof.json`。证明包含目标仓库、PR
   head/base、当时的必需检查、Story 凭证集合、最终 Review 绑定和候选身份；它是机器输入，不是
   签名。staging 必须再从受信任 candidate artifact 回读同一身份，并核对三份证明各自来自发布政策
   列出的唯一仓库，当前 PR 与检查仍和证明一致。
4. 三仓证明由维护者命令写入各自 PR 的唯一 owner 评论。staging 的预批准任务直接读取固定三个公开
   仓库的 PR、评论与检查，验证后生成不可变交接 artifact；人工批准后的任务再次读取三仓并要求
   重算集合完全一致，随后才取得 stage-only OIDC 身份。

### 全量检查复用

1. 只复用同一次 `runLoop` 中由引擎刚执行、全部通过且完成后再次核对 HEAD/干净检出的全量契约检查。
   不落盘做跨运行缓存，避免 agent 可写 workspace 把自述伪装成引擎事实。
2. 复用证明绑定精确 head、默认分支基线、质量契约摘要、平台和实际验证环境摘要。最终 Review 先完成
   自己的远端/PR/base 契约预检；只有所有字段相等才跳过重复命令，否则沿用原路径重跑。
3. TDD 门禁不是质量契约全量检查的一部分，仍保持独立执行与凭证语义。

Python 多包真实候选随后证明，Validator 仍重跑同一全量检查会在断网隔离中产生假“不可验证”。
ADR-028 的补充实施现把实际检查清单写入 Validator 请求：明确覆盖的机械 AC 直接引用，不再重跑；
语义 AC 与清单外能力仍独立验证。详见同日 Validator 全量检查复用计划。

### Issue 最小入口与指标

1. `ready-for-agent` Issue 使用受管模板提供目标、非目标和可逐条判定的验收标准。入口不让模型自由猜
   Issue 是否 ready；缺字段、关闭、PR、标签不符均在改 Git/写远端前停止。
2. 分支名和 workspace 由仓库 + Issue number 确定；运行身份首次建立后持久化，后续命令只允许继续同一
   身份。入口先创建源 PRD 提交和草稿 PR，满足现有 Final Review 必须绑定真实 PR 的要求。
3. 切分支和建立 PR 前立即写入预备状态；首次推送/建 PR、工作区准备、引擎提交尚未推送、CI 等待和
   本地/远端失败均更新同一条带隐藏身份标记的 Issue 评论，PR 建立后原位升级。引擎结束后回读 PR，
   开放状态、目标分支或 head 变化均拒绝可信结论。命令可以在明确边界内推送当前运行分支和更新草稿
   PR，但不合并、不发布、不轮询。
4. ready 起点来自 GitHub label event，不采用本机启动时间。终点必须是当前 PR head 已取得引擎正式
   通过且远端总闸 ready；候选 Shadow 只记录运行结果，不计为可信 PR。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用，三个目标都容易被“有一个文件/有一个命令”伪装成完成。
- **裁决**：以上九项分别给出成功证据与明确失败观察；身份、复用、入口和指标均有机器 schema。
- **验证证据**：发布脚本、workflow、CLI、循环、Review、残留与文档合同测试，以及最终全量检查。

### 2. 生成方不得给自己签发通过

- **适用性**：适用，Agent 能写代码、Issue 评论和普通 workspace 文件。
- **裁决**：候选运行文件由 CLI 自检，绿色证明来自引擎现有凭证和 Review 绑定；staging 独立回读候选
  artifact 与三仓证明。Issue 评论只展示结论，不产生结论。
- **验证证据**：替包、伪摘要、伪 proof、少仓和 Agent 自述成功但门禁失败的回归全部失败关闭。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：Issue 入口新增建分支、推送、建草稿 PR 和评论；不增加合并、发布或删除权限。
- **裁决**：只处理显式 Issue number；启动前要求 clean worktree、ready 标签和无冲突运行；固定分支/PR；
  远端写入均可由关闭 PR、删分支或改评论恢复。npm staging 继续需要受保护环境批准。
- **验证证据**：重复、冲突、关闭 Issue、缺标签、命令失败和中断测试；确认从不调用 merge/release API。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用。
- **原生能力对照**：分支/PR/Issue/Actions artifact 使用 Git 与 GitHub 原生能力；Agent 执行、模型选择、
  worktree 编排不重建，继续走现有 runner adapter 和循环。
- **build/adapt 裁决**：只新增确定性的 Issue 适配、证据合同和检查复用；核心候选/证明 schema 不含
  Claude、Codex、Cursor 或语言生态字段。
- **验证证据**：核心类型 runner-neutral；命令夹具只在 GitHub 适配层出现 provider 字段。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用；当前真实缺陷是三仓人工口头闭环、重复全量检查和测试临时目录稳定增长。
- **裁决**：先写替包/错绑/少仓/输入漂移/重复运行/残留回归，再写成功路径。主要指标为 ready 到可信 PR
  的总时间；辅助记录实际运行、CI 等待、人工继续次数和检查复用节省时间。
- **验证证据**：失败与成功测试成对；全量测试前后临时目录零增长；Issue 指标不因恢复运行而重置。

## 实施顺序

1. 固化测试残留样本，并让测试精确回收自己触发的保留目录。
2. 升级候选打包证据；实现候选 CLI 运行文件树核验与候选身份摘要。
3. 把候选身份接入 Story 当前性、最终 Review 和自动生成的 Dogfood 证明。
4. 增加固定三仓政策、证明验证器和 staging workflow 的跨仓机器读取；staging 在 OIDC 前失败关闭。
5. 给循环增加只在精确绑定相等时可消费的一次性全量检查证明。
6. 增加 ready Issue 模板、单运行编排、可恢复状态写回和总时间指标。
7. 更新 ADR、架构、发布手册、README 与回归说明。
8. 运行定向测试、格式、lint、typecheck、完整测试、build、repository-health 和依赖审计；核对测试前后
   临时目录零增长。本轮不推送、不发布、不改远端规则。

## 完成证据（2026-08-15）

- 候选、发布、复用、Issue、CLI 与受管模板的组合回归通过；最终全库结果为 154 个测试文件通过、
  2438 项通过，另有 6 个文件和 77 项按平台条件跳过。
- 格式、静态检查、类型检查、仓库健康、构建和依赖审计全部通过；本地真实执行了打包、仓库外 npm
  安装、包文件树复核、真实 bin 启动与 Shadow doctor，结果为 verified/退出 7。该本地产物只用于
  烟测，不是正式候选，也没有上传或发布。
- 独立复核发现并关闭了两个原实现窗口：旧三仓证明没有绑定当前 base 和检查重跑，人工批准等待期间
  也没有再次读取三仓；Issue 首次建 PR/工作区准备失败会只留本机，且引擎返回后没有回读 PR。现均有
  失败回归，staging 在批准前后各读一次三仓，Issue 入口失败和 PR 竞态都会写回失败。
- 两个故意保留验证现场的测试在 Node 真实临时目录中单独复跑；既有 216 个历史目录的路径集合摘要
  前后完全相同，本轮零增长。历史目录未被本轮越权删除。
- 本轮没有推送、合并、创建真实 Issue/PR、运行远端 staging、发布 npm 或修改远端规则。三仓批准和
  ready Issue 总时间目前取得的是可重复的本地合同证据；首次真实数据必须在本改动合并并正式发布、
  目标仓固定相同版本后产生，不能把本轮测试数字冒充生产指标。
