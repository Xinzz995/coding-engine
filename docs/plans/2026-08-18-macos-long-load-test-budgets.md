# macOS 长负载测试预算与串扰修复

## 问题与边界

0.37.0 第三个重建候选在 PR #264 的远端运行 `32046557511` 中，Linux/Windows 通过，但
macOS 24 的受管权威快照重试用例超过 30 秒，macOS 22 的完整干净检出用例超过 60 秒。后者超时
后异步 runLoop 继续安全收口，与紧随其后的清理用例重叠，使后一个用例得到错误退出码。这是测试
预算与隔离残留，不是产品行为失败；不能靠重跑远端检查制造绿色。

本计划由政策例外 Issue #265 跟踪。只修改两个测试用例的有界预算；不修改任何产品命令、运行时
超时、进程监督、GitHub 读取、候选证明或发布行为。

## 可证伪完成合同

| # | 完成条件 | 通过证据 | 失败观察 |
| -: | --- | --- | --- |
| 1 | authority snapshot 重试用例在整套负载下有足够时间完成受管失败、退避、重试和收口 | 目标用例连续重复通过；axis 次数断言不变 | 仍超时，或通过删除重试/收口断言换绿 |
| 2 | clean validation 主流程在预算内自然完成，后续清理用例不与其后台流程重叠 | 两用例连续成对运行，退出码与检出清理断言稳定 | 首用例超时，后用例偶发退出 1 或留临时检出 |
| 3 | 只调整测试预算，不改变产品时限和结论 | Git diff 只含两个测试与计划/回归文档 | 修改 src 非测试逻辑、放宽产品 timeout 或删除失败断言 |
| 4 | 新候选重新完成 #250 | 新 main、新 candidate run、新 PR/workspace 与单次补签实证 | 复用 32043375321、PR #264 或旧 workspace |

## 设计裁决

1. authority snapshot 重试用例从 30 秒提升到 60 秒，覆盖一次受管失败重试的真实额外成本。
2. clean validation 完整主流程从 60 秒提升到 90 秒，给 Validator 干净检出、TDD、凭证和收口保留
   50% 调度余量。紧邻的清理失败场景保持原 60 秒预算，用于证明级联症状随前一用例自然完成消失。
3. 不改全局 Vitest 预算；其余短用例继续保持原上限。

## 黄金原则逐项对照

1. **可证伪完成合同**：以上四项均有明确成功与失败观察，远端原失败日志是反例基线。
2. **生成方不得自签**：预算变化不改变任何产品结论；原退出码、次数、路径和清理断言全部保留。
3. **自治与可逆性**：不增加自治能力；回退只需恢复两个用例的 timeout。
4. **原生执行优先**：继续使用 Vitest 单用例 timeout，不新增调度器或自定义重试。
5. **假绿与恢复优先**：先连续复现相邻用例，再跑完整文件和全量矩阵；禁止用远端重跑替代修复。

## 验证顺序

1. 两个目标用例及 clean validation 相邻用例连续成对运行。
2. 两个测试文件完整回归。
3. 格式、lint、类型、构建、仓库健康、依赖审计和完整测试。
4. 受保护 PR 与七套远端矩阵通过后合并，再从新 main 重建候选。

  `coding-x-*` 集合恢复到测试前相同的 4462 项与同一摘要。
