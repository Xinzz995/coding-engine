# 干净验证检出保留可达 Git 历史实施计划

## 背景与完成合同

0.34.0 候选在 coding-engine 自托管 Shadow 验证中出现了可稳定复现的误阻断：Developer 所在仓库
保留完整历史，1990 项测试通过；引擎的独立验证检出只以 `--depth=1` 获取当前提交，使逐文件
`git log` 把当前 HEAD 误当成所有现存文件的首次提交，两份实际未变化的 ADR 因此被文档健康检查
错误判为过期。

Issue #148 跟踪本次修复。候选运行 30844326491 及其摘要
`db2c22f440d5d912dc195e9e8541ce0e5b54a8d1b275a9421949ce9eebcd382e` 已作废，Engine PR #147、
Go PR #18 与 Python PR #15 不得用于 npm staging。

| 验收标准                 | 通过证据                                                                                 | 失败观察                                                          |
| ------------------------ | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 未修改文件保留逐路径历史 | 两次提交只改第二个文件，验证检出对第一个文件查询到首次提交                               | 浅检出把最新 HEAD 误报为第一个文件的最近变更                      |
| 精确提交身份保持不变     | 检出仍为目标 HEAD 的 detached checkout，index tree 与目标 tree 一致                      | 为保留历史改写 HEAD、父提交或工作树                               |
| 只复制必要历史           | 只获取目标 HEAD 与附加提交可达的祖先，不抓取无关分支或标签                               | 全量镜像仓库 ref namespace，或依赖原仓库对象目录                  |
| 不完整来源失败关闭       | shallow/partial、缺失对象、replace refs 与 grafts 在项目命令前明确拒绝                   | 自动联网补对象，或用改写后的历史继续签发验证结果                  |
| 历史资源有界             | 可达对象超过 10 万或保守容量估算超过 1 GiB 时在 fetch 前拒绝，并复核检出对象文件实际大小 | 用源仓库 delta 压缩值低估目标占用，或下载无界历史后才发现无法核对 |
| 旧回执自动失效           | clean checkout 协议升级为 v3，环境摘要变化                                               | v2 receipt 继续显示当前通过                                       |
| 原缺陷进入真实回归       | coding-engine 的 repository-health 在干净检出中通过                                      | 只跑合成测试，不复查实际失败路径                                  |
| Windows 测试预算相互隔离 | 普通 Windows 测试在每项开始前重置替身计数，单项第 10,001 次仍失败                        | 多项合法测试累计耗尽共享额度，或直接提高额度掩盖问题              |

## 设计裁决

1. 去掉精确提交 fetch 的 `--depth=1`，保留目标 HEAD 和附加提交的完整可达祖先；继续使用独立临时
   Git 仓库，不注册 worktree、不保留指向开发仓库的 alternates，也不抓取无关分支或标签。
2. fetch 前在来源仓库只读核对：shallow、partial/promisor、缺失对象、replace refs 与 grafts 均直接
   返回不可验证，并关闭 Git 的自动补取和替换历史能力。目标提交集合最多 16 个，去重可达对象最多
   10 万个；容量以每个对象未压缩大小加 1% 和 1 KiB 固定余量做保守估算，最多 1 GiB，不再使用
   可能被 delta 压缩严重低估的源仓库磁盘占用。
3. fetch 后必须证明目标对象集合与预检集合完全一致、没有复制任何 ref namespace，并复核目标
   `.git/objects` 普通文件实际大小不超过 1 GiB。历史准备与工作树 materialize 共用现有十分钟绝对
   截止时间，不因拆成两个受管进程而重置；固定 Git executable、关闭系统与全局配置、Git 控制面冻结、
   拓扑检查和安全清理保持不变，项目命令改写历史对象仍会阻断。
4. 协议升级为 `clean-checkout-v3`。已有 v2 回执与 Final Review 因环境摘要变化自动失效，不能复用。
5. 修复后关闭而不合并三个旧候选 PR，从修复后的新 main 重建同版本候选，并用全新 workspace 重跑
   coding-engine、Go 与 Python；三个项目仍必须安装同一 tarball。
6. 普通 Windows 测试替身的 10,000 次调用上限按单项测试计算，消除测试顺序和文件体积耦合；
   Windows 原生标准用户证明继续使用生产 transport，不加载重置 setup。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用。上表给出了逐路径历史、精确 HEAD、资源上限和真实回归的正反观察。
- **裁决**：不靠刷新 ADR 日期、跳过 repository-health 或重跑掩盖问题。
- **验证**：合成两提交回归、浅仓库与超限反例、实际 repository-health、全量检查与三仓 Dogfood。

### 2. 生成方不得给自己签发通过

- **适用性**：适用。缺陷发生在引擎独立机械门禁，而 Developer 自报为绿色。
- **裁决**：引擎只接受独立检出中的机械结果；Developer 的 1990 项通过不能覆盖独立失败。
- **验证**：回归测试先证明浅历史会产生错误提交身份，再由 v3 检出给出独立正确结果。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：不扩大 Agent 权限，但扩大验证检出的读取输入和临时磁盘范围。
- **裁决**：增加来源完整性、对象数量、保守容量、目标实际大小、受管超时与清理边界；超限返回不可验证。
- **验证**：浅来源、部分来源、缺失/替换/嫁接历史、对象超限、字节超限、无关 ref、Git 控制面改写和清理测试。
- **Windows 测试边界**：不放大 10,000 次上限；每项测试独立计数，并继续单独运行原生标准用户证明。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用且与项目语言无关。
- **原生能力对照**：使用 Git 原生可达历史与逐路径查询，不代理或重写项目的 Git 命令。
- **裁决**：历史准备只位于 clean checkout 控制平面，不给下游增加 Node/npm 假设。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用。本次是 Dogfood 发现的真实误阻断，同时浅历史也可能让其他历史检查假绿。
- **裁决**：把真实失败固化为回归；旧候选和旧三仓结果全部作废，从修复后的候选重跑。
- **验证**：repository-health 不再误判、旧 v2 环境摘要失效、三仓使用同一新摘要完成闭环。

## 实施与发布顺序

1. 先增加逐路径历史、shallow 来源和资源预算失败测试，确认旧实现失败。
2. 实现受界的完整可达历史 fetch，升级 clean checkout 协议并更新 ADR-022。
3. 通过格式、静态、类型、全量测试、构建、repository-health 和依赖审计。
4. 创建受保护 PR，等待跨平台 CI 后合并；关闭而不合并三个旧候选 PR。
5. 从新 main 重建 0.34.0 候选，用全新 workspace 重跑三仓，再进入 npm staging。
