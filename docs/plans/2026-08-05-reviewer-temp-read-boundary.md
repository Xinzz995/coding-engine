# Final Reviewer 临时目录读取边界安全修复

## 目标与事实起点

本计划落实 GitHub Issue #175。coding-x 0.34.0 的 Codex Reviewer 权限配置只声明
`:minimal = read` 和审查包绝对路径可读，却没有显式拒绝 `:root`、`:tmpdir` 与
`:slash_tmp`，并把沙箱网络设为开启。生产隔离探测又把审查包和包外 canary 一起放在
`os.tmpdir()` 的同一临时根中。

2026-08-05 使用与 0.34.0 相同的 Codex 参数、`codex-cli 0.146.0-alpha.9.2` 和
`gpt-5.6-sol` 做一次性反测时，Reviewer 真实返回了审查包外 canary 的原文。canary 是专为
反测创建的假秘密，没有读取真实用户秘密；写文件和删除保护文件均被只读边界拒绝。加入
`:root = deny`、`:tmpdir = deny`、`:slash_tmp = deny`，只重新开放审查包，并把沙箱网络
关闭后，同一系统临时目录反测返回 `outsideSecret = null`，写入、删除和外部能力均为 false。

PR #172 继续保持未合并和 `unverifiable`。不得用重复运行得到的偶然绿色覆盖本次证据。
本修复使用独立 PR 和补丁版本，不混入 R7 文档改动，也不修改或合并 PR #65。

## 范围与非目标

本轮只处理 Final Reviewer 的 Codex 权限与隔离证据：

- 默认拒绝文件系统根、系统临时目录和 `/tmp`，保留 `:minimal` 所需系统读取，并只为精确
  审查包根重新开放读取；
- 关闭 Runner 沙箱网络；模型服务自身连接不由该沙箱网络开关提供，必须以真实调用验证；
- Codex 的 `externalToolSucceeded` 不再被特殊忽略；提示词明确只有成功且得到可用结果才为
  true，被拒绝、不可用或报错必须为 false；
- 将事件形状损坏、已知禁用工具事件和未知非被动事件映射为固定诊断类别，并保留输出字节数
  与 SHA-256，不回显事件名称、参数、路径、模型文本、源码或秘密；
- Runner 工具策略升级为 `package-read-only-v7`，同时把 Review 规则版本升为 `1.3.0`，使旧
  Review 绑定失效；工具策略的独立绑定字段仍由 #166 处理，本补丁不扩状态 schema。

本轮不把被拒绝的工具事件放入宽松白名单，不切换模型，不在 GitHub 调用模型，不改变三层
Review 内容、findings 裁决或远端门禁。当前 Codex CLI 仍会把 `apply_patch` 和 `view_image`
展示给模型；0.146 没有受支持的完整关闭开关。因此本轮可证明的是“包外不可读、包内只读、
不能写、不能执行危险副作用、沙箱无网络”，而不是虚构“模型完全看不到任何工具”。正常
Review 中出现工具事件仍立即阻断；隔离反测只有在所有机械副作用与结果字段均安全时才通过。

## 设计裁决

1. 权限安全依赖显式 deny，不依赖“未写规则等于默认拒绝”的假设。`tmpdir` 和 `/tmp` 必须
   单独拒绝；精确审查包绝对路径以更具体规则重新开放 read。
2. 评审包内容仍通过绑定 Git 对象构造并作为提示数据交给模型。Codex 内置的只读文件能力可见
   不等于扩大可信输入；其访问仍受相同权限 profile 约束。
3. 正常 Review 与隔离反测的完成语义不混合：正常 Review 不应调用工具；隔离反测会主动尝试
   越界，但只有 host 观察到 canary 未泄露、树未变化、写删失败、外部能力未成功时才可能通过。
4. 模型自述不能证明隔离安全，但危险自述必须按最保守语义阻断。引擎的文件副作用、输出扫描
   和临时树核对仍是主要机械证据。
5. 事件名称可能受模型或未来 CLI 影响，不直接进入用户诊断。实现只映射到固定枚举；未知项
   保持阻断。输出摘要用于复现身份，不用于把第二次成功覆盖第一次失败。
6. 0.34.0 无法可信批准自身安全补丁。本轮通过旧 GitHub 机械门禁、限时政策例外、人工核验和
   真实攻击反测完成紧急补丁发布；补丁发布后再由新稳定版正式评审 PR #172。

## 原生能力核对

- Codex CLI 0.146 的权限 profile 原生支持文件系统和网络 deny，应直接适配，不另建沙箱。
- 0.146 没有 `apply_patch` 或 `view_image` 的受支持禁用项；`image_generation` 与本地图像读取
  不是同一能力。0.147 只新增 `view_image` 开关，仍不能完整关闭 `apply_patch`。
- 因此供应商差异继续收口在 Codex adapter；runner-neutral 的三态、Review 轴和远端状态合同
  不变。

## 实施与验证顺序

1. 先提交本计划和失败测试，固定 0.34.0 的错误参数与包外 canary 场景。
2. 修正 Codex 权限参数、网络开关、探测提示语义和固定诊断分类。
3. 升级工具策略版本，补齐 Review 绑定失效测试。
4. 运行定向 Runner/Final Review/规则测试，再运行完整本地门禁与构建。
5. 在一次性系统临时目录中执行真实 Codex 攻击反测，确认 canary 未泄露、写删失败、无残留。
6. 通过受保护独立 PR 合并，发布补丁稳定版；随后更新质量契约固定版本并重新完成 PR #172。

## 黄金原则对照

| 原则 | 适用性与设计裁决 | 证据 |
|---|---|---|
| 1. 可证伪完成合同 | 适用。AC-1 至 AC-9 均定义成功、失败信号与验证方式 | 参数、canary、副作用、脱敏、版本与全量门禁测试 |
| 2. 生成方不得自签 | 适用。模型的 false 不能单独证明安全；host 机械检查负责裁决，模型的危险 true 只能导致阻断 | `true` 自述、真实 canary、文件树与输出扫描反例 |
| 3. 自治扩大同步防线 | 本轮不扩大自治，收紧读取和网络；未知事件、配置漂移和攻击成功均不可验证 | deny 参数、无网络、未知事件 fail-closed |
| 4. 原生能力优先 | 适用。直接使用 Codex 权限 profile；CLI 无完整 no-tools 能力的差异只留在 adapter | 本机 CLI、官方权限文档和精确版本能力审计 |
| 5. 假绿与恢复 | 适用。先固化真实 canary 泄露，再证明修复；旧 Review 失效且 PR #172 不提前合并 | failure-first fixture、真实反测、v7 绑定、独立补丁发布 |
