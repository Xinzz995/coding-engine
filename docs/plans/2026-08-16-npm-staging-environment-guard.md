# npm 暂存环境防漂移检查

## 目标与边界

把已经在 GitHub 生效的 `npm-staging` 单人批准规则变成每次暂存前的机器输入，防止远端配置被改弱后
工作流仍继续进入 npm。固定规则是：至少存在一个批准人，允许单人管理员批准自己的运行，管理员不得
绕过批准，只允许 `main` 分支进入环境。仓库政策不绑定批准人的具体账号；当前批准人是谁由 GitHub
环境配置管理。

本轮不增加自动批准、轮询、队列、更多管理员、其他发布环境或 npm 发布能力。远端批准仍由维护者
显式完成；检查失败时只停止运行，不修改 GitHub 设置。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用，远端界面显示正确不等于以后仍正确。
- **裁决**：以上四项都给出成功证据与具体失败观察；机器检查接受两个 GitHub API 快照，不接受自由文本。
- **验证证据**：政策与脚本单测、workflow 结构测试、当前远端响应烟测和完整仓库检查。

### 2. 生成方不得给自己签发通过

- **适用性**：适用，仓库代码不能证明远端环境仍按同一规则运行。
- **裁决**：预批准任务现场读取 GitHub 返回的环境与分支政策；仓库政策只定义预期，不充当实际状态。
- **验证证据**：仓库政策保持不变但远端夹具被逐项改弱时全部拒绝；替换为另一名合法批准人的夹具与
  真实 API 回读独立通过。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：不扩大自治范围；不新增写远端、批准或发布动作。
- **裁决**：新增的是发布前拒绝条件。误判时可由撤销本 PR 恢复，且失败发生在 npm 身份和人工批准之前。
- **验证证据**：workflow 顺序断言检查环境核对早于候选下载、environment 等待和 npm 暂存。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用。
- **原生能力对照**：继续使用 GitHub environment、required reviewer 和 deployment branch policy；不自建批准系统。
- **build/adapt 裁决**：只增加 GitHub API 快照适配和确定性比较，候选身份与 runner-neutral 引擎合同不变。
- **验证证据**：供应商字段只存在于发布政策、发布证据脚本和 GitHub workflow。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用；真实发现是仓库 ruleset 不会让 environment 的 “protected branches” 模式自动识别
  `main`，旧配置实际允许所有分支进入。具体批准人不是安全边界，不在代码里绑定个人账号。
- **裁决**：先固定允许绕过、错分支、无批准人和非法批准人结构的失败样本，再验证当前正确配置；以
  “弱化配置仍进入暂存”的假绿数必须为零为本轮指标。
- **验证证据**：逐项反例、当前公开 API 响应、本地全套检查，以及真实等待运行 `31920215881` 已证明
  正确配置会要求批准且取消前未执行 npm 动作。

## 实施顺序

1. 新增受保护的暂存环境政策与严格验证命令。
2. 在 `stage-candidate.yml` 的第一段预批准任务中用只读工作流身份读取并验证远端配置。
3. 增加成功、逐项弱化、workflow 顺序和稀疏检出回归。
4. 修正发布手册，运行当前远端响应烟测和仓库全部必需检查。
5. 通过限时政策例外提交受保护路径变更；合并后关闭例外并确认主分支干净同步。
