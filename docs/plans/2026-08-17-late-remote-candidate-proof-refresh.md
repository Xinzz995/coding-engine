# 晚到远端检查的候选凭证补签

## 问题与边界

0.36.1 三仓实证暴露了一个确定的恢复缺口：Shadow Story 验收和本地最终 Review 已经完成，但远端
检查在 Review 收口后才变为 ready 时，引擎不会生成 `candidate-proof.json`。现有
`candidate publish-proof` 只会发布已有证明，无法刷新远端状态并补签，维护者因此只能重跑约半小时
的最终机械检查与 Review。

本轮只补这条恢复路径，不增加轮询、队列、自动合并、自动发布或 Agent 编排。命令仍由维护者显式
运行；它不重跑 Builder、Validator、质量检查或三个 Review 轴。

## 可证伪完成合同

| # | 完成条件 | 通过证据 | 失败观察 |
| -: | --- | --- | --- |
| 1 | `candidate publish-proof --candidate-evidence <packed.json>` 会再次逐文件证明当前 CLI 是原候选，并在短租约内刷新当前 PR 的远端状态 | 候选身份、Story 环境和最终 Review 绑定相等的测试；真实命令路径只调用受管状态观察 | 只凭 workspace 中的摘要补签，或重新调用完整检查/模型 Review |
| 2 | 已有本地 Review 仍为当前、Shadow、通过，且刷新后的远端总闸 ready 时才写入证明 | 成功测试得到新 `candidate-proof.json`，其远端时间和检查来自本次刷新 | pending、failed、invalid 或本地结果过期时仍写证明 |
| 3 | 刷新期间 Story、提交、PR/base、契约、Runner 或 Review 绑定变化时失败关闭且不覆盖旧证明 | 每类竞态由受管当前性结果拒绝；写入次数保持为零 | 观察到一半新状态、一半旧状态后仍补签 |
| 4 | 补签后继续沿用现有 owner、仓库、分支、PR、head/base 和可合并状态核对，再创建或更新唯一证明评论 | 发布适配器原回归继续通过；命令组合测试证明刷新失败时不调用评论写入 | 只生成本地文件却宣称已发布，或绕过现有发布核对 |
| 5 | 不提供候选证据时保持旧行为：只能发布已经存在的证明；缺少证明时明确提示补充证据 | 兼容测试与 CLI 参数测试 | 旧自动化被强制改变，或无证据时暗中生成新证明 |
| 6 | 输出区分“复用已有证明”和“已刷新并补签”，并记录刷新耗时 | JSON/文本输出测试 | 把整次旧验证耗时或等待时间伪装成刷新耗时 |

## 设计裁决

1. 候选证据可用于 `candidate publish-proof`，但不要求同时传 `--shadow`。该命令启动时仍从当前实际
   包根逐文件核对 `packed.json`，不能从 agent 可写 workspace 反推候选身份。
2. 有候选证据时，命令获取新的 `candidate-proof` 短租约，复用现有受管状态观察：重新核对 Story
   凭证、最终 Review、Runner、Git/PR/base/契约和远端 Ruleset/checks，并在慢观察之后再次夹取当前性。
3. 只有受管观察返回当前 Review、候选 Story 环境仍绑定同一候选摘要、刷新远端为 ready 时，才以
   本次远端快照构造并原子替换 `candidate-proof.json`。原 Final Review 文件不改写。
4. 短租约安全关闭后才沿用现有发布适配器写 PR 评论。若评论阶段遇到 PR/head/base 变化，保留本地
   新证明但拒绝发布；staging 仍会独立回读三仓当前状态。
5. 没有 `--candidate-evidence` 时不生成任何新结论，只保留原“发布已有证明”行为。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用，目标不是增加一个命令入口，而是证明没有重跑也没有降低可信度。
- **裁决**：以上六项分别绑定成功、拒绝、竞态、兼容和耗时观察。
- **验证证据**：候选补签单测、CLI 参数/组合回归、workspace 租约 schema、定向与全量门禁。

### 2. 生成方不得给自己签发通过

- **适用性**：适用，workspace、候选摘要文本和 PR 评论都可能由 Agent 改写。
- **裁决**：当前候选运行文件由 CLI 逐文件核对；Story、Review 与远端结论由引擎受管观察重新夹取；
  评论仍不产生结论，staging 继续独立重验。
- **验证证据**：错候选、过期 Review、非 ready 远端和观察竞态全部零写入、零发布。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：命令新增一次 workspace 文件写入，但不新增远端权限，仍只更新现有 owner 评论。
- **裁决**：写入受短租约保护且只替换单一证明文件；远端发布继续核对 owner、仓库、PR 与 head/base；
  不合并、不发布 npm、不修改分支。
- **验证证据**：活动租约冲突、关闭失败、PR 漂移和评论重复路径继续失败关闭。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用。
- **原生能力对照**：GitHub checks、Ruleset、PR 与评论仍通过现有 GitHub 适配器；不复制 CI 或 Agent
  执行能力。
- **build/adapt 裁决**：只组合已有候选身份、受管 currentness 和证明生成器；核心 schema 不加入
  runner 或 GitHub 私有的新字段。
- **验证证据**：新增逻辑位于候选控制平面，现有 Runner 与质量门禁实现不变。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用；真实失败恢复目前约需半小时重复工作。
- **裁决**：先覆盖 pending/failed/stale/race 等拒绝路径，再覆盖 ready 成功；命令报告本次刷新耗时。
  目标是把“远端转绿到证明发布”的恢复从完整 Review 时长降为一次受管状态刷新时长，同时保持零假绿。
- **验证证据**：调用边界测试证明不触发完整门禁和模型 Review；真实 Dogfood 在合并后的新候选上记录
  刷新耗时，不能用单测时间冒充生产指标。

## 实施顺序

1. 放开候选发布命令的候选证据参数，并增加独立 workspace owner 命令。
2. 组合候选身份、受管 currentness、远端刷新和证明原子写入。
3. 保持旧发布适配器，补齐无证据兼容、失败零发布和输出耗时测试。
4. 更新 ADR-027、架构、发布手册、README 与 Dogfood 回归。
5. 运行格式、lint、typecheck、定向测试、完整测试、构建和仓库健康检查；通过受保护 PR 合入。

## 完成证据（2026-08-17）

- 新补签单元测试覆盖晚到 ready、pending/failed、旧 Review 失效、Story 集合错绑、候选摘要传递、
  单次受管刷新和失败零写入；候选发布兼容测试证明无已有证明、无候选证据时零 Git/GitHub 调用并
  明确提示恢复参数。CLI 参数与 workspace owner schema 回归同时通过。
- 完整测试结果为 155 个测试文件通过、2453 项通过，另有 6 个文件和 77 项按平台条件跳过，总耗时
  1624.23 秒。测试前后 218 个既有 `coding-x-validation-*` 目录的路径集合摘要均为
  `de894e0ff50f598f7668c7a66b063b35998ed0f0a5bfeee5a17854403ca65c99`，本轮零增长。
- 格式、lint、typecheck、构建、仓库健康、生产依赖审计和 0.33.3 旧版本 workspace 兼容检查通过；
  构建后的真实 help 已展示新入口。
- 仓库外本地临时候选完成打包、安装和运行文件树自证，随后用真实 bin 获取新的
  `candidate-proof` 短租约。因为烟测 workspace 没有 Final Review，命令按预期退出 2、零证明写入，
  且活动租约安全释放；另一条无候选证据烟测也在任何 Git/GitHub 调用前给出明确恢复提示。两份临时
  目录均已移入废纸篓。
- 本地烟测不是正式候选，也没有模拟远端 ready 后的生产耗时。首次合并后候选 Dogfood 必须让
  Final Review 先记录 pending、等待同一 head 的 CI 自然 ready，再执行一次补签命令，记录其
  `refresh.durationMs` 并与此前约半小时整套重跑对比；这项下游实证不能由本轮测试替代。
