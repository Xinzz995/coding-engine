# Validator 复用同输入全量检查

## 问题

0.36.0 候选在 Python 多包仓完成引擎全量检查后，Validator 又在断网隔离环境中重复执行 wheel
构建，并因再次下载构建依赖而进入“无法验证”。这不是实现失败，而是 ADR-005 保留的重复验证策略
与本轮“准确输入完全一致时复用引擎结果”的路线冲突。现有 ADR-028 只消除了最终 Review 的重复，
没有覆盖 Validator；`prd-to-json` 还会给每个 Story 强制追加与项目质量契约无关的
`Typecheck passes`，在没有独立类型检查器的 Python 仓制造了不可满足的验收项。

## 完成标准

| # | 完成条件 | 通过证据 | 失败观察 |
| -: | --- | --- | --- |
| 1 | Validator 请求携带本轮刚完成的引擎全量检查证明 | 请求包含精确 head、默认分支、质量契约摘要、平台、输入摘要和实际执行检查列表 | 只写“检查通过”，无法对账输入或检查范围 |
| 2 | 只有完整通过且结束后 HEAD、干净检出仍一致的结果可进入请求 | 失败、局部执行、旧式检查或结束后漂移均不产生证明 | 失败或旧结果仍能让 Validator 跳过检查 |
| 3 | Validator 对证明明确覆盖的机械 AC 直接引用引擎结果，不重复执行相同命令 | 指令合同和真实 Python Dogfood 均不再次运行 pytest/wheel/Ruff | Validator 在同一检出中再次运行全量门禁 |
| 4 | 语义验收仍由 Validator 独立完成 | 代码范围、行为、边界和不可变性仍逐条检查并提交 claim | 把“全量检查通过”扩大成整个 Story 自动通过 |
| 5 | 未被证明覆盖的显式 AC 仍失败关闭 | 没有对应检查时不得把泛化的类型检查要求算作已证明 | 以 Ruff、构建或模型猜测冒充不存在的类型检查 |
| 6 | `prd-to-json` 不再给所有语言和仓库强制追加 `Typecheck passes` | skill 合同测试确认质量契约与 Story AC 分层 | Go/Python/文档仓仍被自动塞入 Node 风格标准 |
| 7 | 旧 workspace 和自定义 Validator 保持可读可运行 | 请求中的机械证明为可选扩展，result v2 与现有凭证绑定不变 | 协议升级导致旧结果或审计 Runner 无条件失效 |
| 8 | 最终 Review 的精确复用继续成立 | ADR-028 既有漂移测试和全套测试通过 | 修 Validator 时削弱最终 Review 的重跑边界 |

## 设计裁决

1. 复用现有内存 `FullGateProof`，为其补充由冻结质量契约机械派生的实际检查清单；不创建第二套缓存。
2. 将证明作为 validation request v2 的可选、引擎生成字段。它不改变 Validator result schema，
   也不替 Validator 签发语义结论；唯一用途是让 Validator 对机械 AC 引用已完成事实。
3. Validator 只可复用证明中列出的检查。代码行为、范围、测试是否被篡改、业务边界等仍须独立检查；
   显式 AC 若要求证明清单中不存在的能力，必须自行取得证据，否则按无法验证处理。
4. `prd-to-json` 继续从质量契约冻结 `qualityChecks`，但不再把通用质量要求复制进每个 Story。
   来源 PRD 自己写出的机械 AC 保留，由 Validator 用证明对照，不做字符串删除或猜测迁移。
5. 证明仍只活在同一次 `runLoop`；跨进程继续运行会重新跑全量检查，保持 ADR-028 的保守边界。

## 黄金原则对照

1. **可证伪完成合同**：以上八项分别给出可观察成功与失败；真实 Python 仓是最终反例回归。
2. **生成方不得自签**：Developer 不能产生证明；证明只来自引擎受管检查，Validator 仍独立判断语义 AC。
3. **自治与可逆性对称**：不增加远端权限或持久缓存；请求字段可选，回退只需恢复旧指令与 skill 规则。
4. **复用原生执行面**：继续运行目标仓质量契约的原生命令；只在控制面传递既有结果身份。
5. **失败恢复优先**：任何输入不一致、检查不完整或覆盖关系不明确都重跑或无法验证，不猜测通过。

## 验证顺序

1. 单测冻结证明清单、请求渲染、失败/局部结果拒绝和 skill 不再强制类型检查。
2. 定向运行 validation protocol、full gate、loop instruction 和 loop gate/review 测试。
3. 运行格式、静态检查、类型检查、构建、仓库健康、依赖审计和完整测试。
4. 从新 main 重建候选；不用额外 Python wheelhouse 或宿主环境注入，重做三仓 fresh Shadow。
