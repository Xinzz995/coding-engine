# 单调截止时间提前唤醒修复计划

## 背景与根因

PR #241 的 Quality Gate 运行 31922130878 在 macOS / Node 24 暴露了一个既有竞态：
`bounds ACK/final exit when a drained supervisor remains alive` 本应报告 ACK 或最终退出阶段超时，
却报告了后续 quarantine 安装超时。同一共享截止时间刚产生第一处超时后，quarantine 仍能看到正的
剩余时间并开始执行，说明运行时计时器曾在单调时钟真正到期前唤醒；当前 `MonotonicDeadline.run()`
把这次提前唤醒直接裁决为超时，随后次要补救失败覆盖了真实故障阶段。

本轮修正截止时间原语：运行时计时器唤醒时必须再次读取单调时钟；若尚有剩余时间，就按剩余预算
继续等待。它不延长绝对截止点，不改变失败关闭或隔离状态，也不放宽既有收尾断言。

## 可证伪完成合同

| 验收标准               | 通过证据                                                | 失败观察                   |
| ---------------------- | ------------------------------------------------------- | -------------------------- |
| 提前唤醒不签发超时     | 假时钟停在截止点前，运行时计时器触发后 Promise 仍未结算 | 尚有剩余预算却返回 timeout |
| 到达原截止点后立即失败 | 假时钟推进到固定截止点，下一次唤醒返回既有 timeout      | 新建或延长完整预算         |
| 收尾阶段诊断不再被掩盖 | POSIX 故障注入仍只接受 `/post-drain                     | ACK                        | exit/` | 放宽到 receipt 或 quarantine 文案 |
| 安全语义不变           | receipt、quarantine 与 isolated 的原有断言原样保留      | 删除、弱化或改写安全断言   |
| 高负载回归稳定         | 定向用例至少 30 次独立通过，并通过全量检查              | 只依赖一次重跑绿色         |

## 实施边界

1. 只修改单调截止时间原语、它的测试和本计划；不改变 POSIX/Windows 协议、时限数值或发布功能。
2. 不增加第二份预算。提前唤醒后只能消费同一绝对截止点的剩余毫秒数。
3. 用独立假单调时钟制造“运行时计时器已响、单调时钟尚未到期”的确定性反例，不用 sleep 猜竞态。
4. 保留现有收尾测试的严格错误类别和全部安全落盘断言。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用。上表区分提前唤醒、真正到期、收尾诊断和安全状态。
- **裁决**：只有注入的单调时钟到达固定截止点，才允许产生 deadline 错误。
- **验证**：假时钟反例、真实 POSIX 故障注入、30 次独立重复和全量检查。

### 2. 生成方不得给自己签发通过

- **适用性**：适用。由 Vitest 机械控制两个时钟并裁决 Promise 是否已经结算。
- **裁决**：不靠错误文案解释通过，先证明截止点前未结算，再证明截止点后失败。
- **验证**：失败测试先覆盖当前实现，修复后保持为永久回归。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：不适用。本轮不扩大 Agent、发布、合并或文件写入权限。
- **裁决**：改动限于共享计时原语，可由单一提交撤销。
- **验证**：最终差异不得修改监督器协议与远端环境规则。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用。POSIX 与 Windows 继续共用同一个单调截止时间原语。
- **裁决**：不增加平台分支；修复发生在共同控制层。
- **验证**：跨平台全量检查必须全部通过。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用。风险不是错误放行，而是错误阶段被覆盖并造成不可诊断的误红。
- **裁决**：不放宽断言、不靠重跑掩盖；用确定性竞态测试消除提前超时。
- **验证**：30 次故障注入、完整本地检查和 GitHub 多平台矩阵。

## 实施顺序

1. 先增加提前唤醒反例，确认旧实现会过早结算。
2. 修改 `MonotonicDeadline.run()`，每次计时器唤醒后重新核对同一单调截止点。
3. 运行截止时间与 POSIX 收尾定向测试，再做至少 30 次独立重复。
4. 运行格式、静态检查、类型检查、全量测试与构建；远端多平台检查通过后收口计划。
