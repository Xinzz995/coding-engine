# 干净验收链接批量核对与完整硬链接组实施计划

## 背景与完成合同

0.34.0 候选在 coding-engine 自托管 Shadow 验证中，于准备后的
`node_modules/.bin/rolldown` 核对处返回不可验证。真实复现表明，逐条启动受管 reader 时 22 条 npm
命令链接已接近 30 秒统一期限。进一步用真实 `npm ci` 检查发现，esbuild 还会在同一
`node_modules/**` 内产生两组完整 hard link；旧规则会在链接超时修复后继续误阻断它们。

Issue #145 跟踪本次修复。候选运行 30805229211 及其摘要
`1d11ea68e15182e7926039acf105efbbe2018c36c981fccda03f51b8b738bf1e` 已作废，旧三仓结果不得复用。

| 验收标准                         | 通过证据                                                                  | 失败观察                                          |
| -------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------- |
| 多条普通文件链接不再逐条启动进程 | 64 条 npm `.bin` 形态在原 30 秒期限内完成，实际 24k 传输边界可自动分批    | 延长期限、静默截断，或仍为每条链接启动一次 reader |
| reader 信任边界不变              | 链接解析、文件系统分类、身份和外部内容仍全部在只读受管进程中完成          | 主进程直接解析链接，或可疑路径自动降级放行        |
| 批次结果精确绑定请求             | schema、请求摘要、索引、顺序、数量、UTF-8、响应大小和 EOF 均有反例测试    | 复制旧结果、乱序、缺项、额外字段或损坏输出仍通过  |
| 数量、时间和字节保持全局上限     | 1025 条在 reader 前拒绝；所有批次共享 30 秒、1024 条和 1 GiB 实际读取预算 | 每批重新获得预算，或读完无界内容后才发现超限      |
| 正常依赖 hard link 可验证        | 同一声明产物根内完整两成员、三成员及两组 esbuild 形态通过                 | 按 esbuild 路径开白名单，或复制文件掩盖工具链行为 |
| hard link 不能跨边界             | 项目外、源码、`.git`、跨产物根、不完整组和不可信文件系统均阻断            | 仅看到产物目录内一个名称就放行                    |
| 扫描期间变化失效                 | 根身份、整树拓扑、hard link 组和后备文件系统身份在末尾重扫一致             | 新增、删除、替换别名或根路径后旧观察仍有效        |
| 旧回执自动失效                   | clean checkout 协议升级为 v2，环境摘要变化                                | v1 receipt 继续显示当前通过                       |

## 设计裁决

1. 不采用主进程 internal fast path。目录替换与复杂链接解析无法在当前权限模型下证明绝不越界；所有
   普通文件链接和内部目录链接继续交给固定受管 reader，保留既有只读与失败关闭边界。
2. reader 使用 v2 批量协议。调用方把 checkout 相对路径按真实内联命令上限贪心分批；每批包含连续
   索引和请求摘要，结果必须保持同一顺序。批次顺序执行并共享一个绝对期限，不并发放大配额。
3. reader 要求普通文件大小有界且前后身份稳定；内部目录链接只有解析链始终留在检出、避开 `.git`、
   最终目标是普通目录且整树证明覆盖目标时才允许。来源和项目外目录链接阻断；外部文件继续执行逐组件
   文件系统检查、descriptor 绑定、内容摘要和精确 EOF 证明。
4. 数量预算在 reader 启动前对所有链接计数。每批启动前只获得共享实际读取上限的剩余额度；同批重复
   目标复用已完成的摘要，跨批或跨调用重复目标保守地重新读取并计费。失败、超时、损坏结果和并发复用
   都会让预算失效，不能通过重试重置额度。目标摘要记录继续用于识别同一身份下的不一致内容。
5. hard link 按 `dev + ino` 建立完整组，不按工具名称例外。成员数必须等于 `nlink`，全部元数据一致，
   且每个名称都属于同一个最深声明产物根。Linux 只接受 ext、XFS、Btrfs、tmpfs；macOS 只接受 APFS、
   HFS；Windows、Overlay、FUSE、网络与未知文件系统失败关闭。
6. 首次拓扑遍历冻结每个目录、文件和符号链接的类型与身份，并建立完整 hard link 组；所有受管链接完成
   后重扫整棵树并比较规范摘要，同时复核根路径仍为同一普通目录、no-mount 与后备文件系统身份。该设计
   检测两个观察点之间持续存在的变化，不声称发现出现后立即撤销的瞬时竞态。
7. clean validation、mount、hard link 与 link reader 都进入旧规则保护路径。PR 关联 Issue #145，使用
   owner 明确批准的政策例外并通过完整机械检查。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用。上表同时写明成功证据与失败观察。
- **裁决**：不以重试、延长期限或删除检查作为修复。
- **验证**：协议反例、真实链接拓扑、全量检查和新候选三仓 Dogfood。

### 2. 生成方不得给自己签发通过

- **适用性**：适用。本缺陷发生在 Validator receipt 签发之前。
- **裁决**：链接和 hard link 只产生机械证明；缺证据即阻断，Agent 自述不参与。
- **验证**：越界、组不完整、跨域和结果损坏都不能转成绿色结果。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：未扩大 Agent 权限，但放行一类真实产物拓扑，属于高风险验证规则变化。
- **裁决**：只接受完整同域组，双扫描复核；协议 v2 使旧证据失效，可通过回退 PR 恢复。
- **验证**：别名新增、删除、外连、跨根和未知文件系统回归。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用且跨语言。
- **原生能力对照**：保留 npm/Python/Go 原生安装行为，只核对其产物；不复制依赖、不改写 hard link。
- **裁决**：批量和完整组证明都位于控制平面，不引入项目技术栈假设。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用。目标是消除正常依赖的误阻断，同时不增加越界假绿。
- **裁决**：任何批次、组或文件系统证据缺失均返回不可验证；旧候选作废后从零重跑。
- **验证**：真实 `npm ci`、64 条命令链接、完整与不完整 hard link 组及三仓候选闭环。
