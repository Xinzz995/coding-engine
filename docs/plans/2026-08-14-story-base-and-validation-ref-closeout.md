# Story 固定起点、验证引用与 0.36.0 发布收口

## 目标与边界

修复本轮 RC1 真实运行暴露的逐 Story 比较范围假绿，并关闭 Issue #210 的干净检出默认分支引用缺口。
完成后废弃现有 0.36.0 RC1，从新 `main` 重建候选、重新完成三仓 Shadow、npm staging、正式发布与
最终同步核对。本计划不实现 Issue 接入、任务队列、自动建 PR 或其他产品外壳。

## 可证伪完成合同

| # | 完成条件 | 通过证据 | 失败观察 |
| -: | --- | --- | --- |
| 1 | Story 第一次实现前由引擎固定起点，所有重试保持不变 | 状态与循环测试观察首次写入、跨轮重试、多 Story 各自起点 | Agent 可改起点、重试改用 `HEAD^` 或后续 Story 复用错误起点 |
| 2 | request、result、evidence 与新凭证绑定起点、终点和变化摘要 | 协议解析、错绑、当前性与旧凭证迁移测试 | 缺任一字段、错起点、错摘要或旧 schema 仍可签发绿色凭证 |
| 3 | 变化摘要覆盖固定起点到最终 HEAD，并要求祖先关系 | 干净检出集成测试核对删除后重加、空变化、历史重写和不可达起点 | 改变最后一个父提交即可让同一 AC 从失败翻绿 |
| 4 | 多 Story 保留不同起点，最终重验仍使用各自固定范围 | 两 Story 真实提交回归，逐项检查 request 与凭证 | 后续 Story 把前一 Story 的完成提交当成自己的原始起点，或所有 Story 被重置成最终父提交 |
| 5 | 干净检出建立冻结的默认分支引用并绑定环境摘要 | `origin/main` 真实命令回归、引用目标/漂移/篡改测试 | 开发仓可运行而检出缺 ref；把 ref 偷换为 HEAD 后仍接受结果 |
| 6 | 缺失默认分支引用在任何 Agent 启动前明确失败 | loop preflight 回归，调用计数保持 0 | 进入 Builder/Validator 后才偶然失败，或静默用其他提交代替 |
| 7 | coding-engine 自身全量质量检查可在新干净检出运行 | format、lint、typecheck、test、build、CLI smoke、audit、repository-health | 继续把 `format:check` 交给远端来绕过本地缺口 |
| 8 | 0.36.0 使用全新候选完成正式发布 | 新 candidate/stage/tag/npm/GitHub Release 同提交同摘要；三个试点使用同包 | 复用旧 RC1、旧回执、旧 PR head 或只完成 npm/GitHub 其中一侧 |
| 9 | 文档和远端事项与事实同步 | ADR/计划状态、#210、#224、发布记录与最终 Git 状态复核 | 代码完成但计划仍写“待实现”，或本地/远端/标签/registry 不一致 |

## 设计裁决

1. `state.json` 为每个 Story 保存引擎独占的完整起点提交。新 Story 只在首次进入实现模式时写入；
   `passes=true` 但起点缺失的旧候选不补造，按不可验证停止。
2. Validator 协议和持久凭证升级：起点、终点、变化摘要与变更路径计数共同构成目标身份。变化摘要由
   干净检出内确定性 Git raw diff 生成，摘要包含算法版本与两端提交。
3. 干净检出在受管历史中确认起点是终点祖先，再计算摘要。Validator 指令明确要求查看整段范围，
   `HEAD^` 不再是合法替代。
4. 质量契约的 `repository.defaultBranch` 决定唯一允许的本地远端跟踪引用；Story 验收在预检中读取并
   固定其提交，Final Review 使用 GitHub 已确认的 PR base SHA。引用名、目标和额外历史都进入干净检出
   环境摘要。
5. 旧凭证保持严格可读，只用于安全失效；不迁移为新凭证。干净检出协议版本同步升级，禁止旧环境绿色
   状态跨版本延续。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用，问题本身就是验收范围没有机器身份。
- **裁决**：以上九项均给出成功证据和明确失败观察；发布完成必须同时覆盖代码、候选、远端和 registry。
- **验证证据**：协议、状态、循环、干净检出、Final Review、真实自托管与发布后外部核对。

### 2. 生成方不得给自己签发通过

- **适用性**：适用，Builder 可以整理提交历史，Validator 也可能自行选择最窄比较范围。
- **裁决**：起点由引擎在 Builder 前固定；变化摘要由引擎计算；Validator 只对固定范围提交 claim。
- **验证证据**：Builder/Validator 改写起点会被恢复；删除后重加与错误摘要不签凭证。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：不扩大 Agent 权限，但增加引擎创建验证 Git ref 的能力。
- **裁决**：只在引擎自有临时仓库创建一个明确引用；名称和目标均固定、进入身份摘要，清理沿用现有
  临时检出归属证明。npm 发布仍按 2FA 人工批准边界执行。
- **验证证据**：非法引用、目标漂移、控制文件改写和清理失败均失败关闭。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：适用且 runner-neutral。
- **原生能力对照**：Git 原生完整提交、祖先判断、raw diff 和 update-ref 已足够；无需复制 Git 历史模型。
- **build/adapt 裁决**：只新增引擎控制面的起点冻结、摘要和临时引用；Claude/Codex/Cursor 协议保持统一。
- **验证证据**：协议与状态类型不含供应商字段，三个 Runner 继续共用同一 request 形状。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用，本轮删除后重加是已发生的真实假绿样本，#210 是已发生的不可验证样本。
- **裁决**：先固化两个失败样本，再覆盖正常单 Story、多 Story、重试和发布路径。目标是把这两类结果从
  “取决于模型如何比较”变为确定拒绝或确定执行。
- **验证证据**：真实样本回归、完整测试、全新 RC 与三仓 Shadow；不以“代码已写完”作为完成。

## 实施与发布顺序

1. 先提交本 ADR 与计划，固定问题边界。
2. 升级状态、Validator 协议、凭证和 evidence，加入 Story 起点所有权。
3. 升级干净检出：默认分支引用、祖先判断和变化摘要。
4. 接入 loop、只读当前性、Final Review、状态/报告与所有兼容读取。
5. 固化删除重加、历史重写、多 Story、引用缺失/漂移和 coding-engine `origin/main` 回归。
6. 更新 README、ADR-025、旧计划状态和发布手册事实。
7. 运行格式、静态检查、类型检查、完整测试、构建、CLI smoke、依赖审计和仓库健康检查。
8. 推送受保护 PR，等待最新 head 全部远端检查和独立 Review，通过后合并。
9. 从新 `main` 构建全新 0.36.0 候选；三个项目以同一摘要完成全新 Shadow。
10. 通过 npm staging 与 2FA 批准发布，建立不可变标签和 GitHub Release，最后独立核对并关闭远端事项。
