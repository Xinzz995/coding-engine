# POSIX closeout 故障注入测试时序实施计划

## 背景与完成合同

Issue #152 记录了一次 Ubuntu / Node 22 真实 CI 失败：测试期望进入 DRAINED 后停止 supervisor，
但原断言没有证明 `onDrained` 已到达，且 100ms 同时覆盖 receipt 验收、故障注入、ACK 与退出。
本次只校准测试，不根据被截断的日志修改生产行为。

| 验收标准 | 通过证据 | 失败观察 |
| --- | --- | --- |
| 故障注入先于结果裁决 | 测试记录并断言 `onDrained` 到达时间与 supervisor PID | 未进入 hook 也接受错误结果 |
| ACK 与退出仍有严格上界 | 从 `onDrained` 时刻计算失败耗时，并保持固定上限 | 从 setup 开始计时，或取消时间上限 |
| 错误类别不放宽 | 完整捕获错误并只接受 `/post-drain|ACK|exit/` | 接受 receipt 或 quarantine 文案掩盖阶段偏移 |
| 安全落盘事实不变 | receipt 存在、quarantine 不存在、session 保持 isolated | 删除或弱化任一现有安全断言 |
| 回归在重复执行下稳定 | 定向用例单次、至少 30 次独立重复及相关测试全部通过 | 依赖一次偶然绿色或重跑同一失败任务 |

## 实施边界

1. 只修改本计划与 `src/workspace-safety/posix-supervisor-closeout.test.ts`。
2. 把测试专用 `ackMs` 调整为 1000ms，为进入故障注入前的 receipt 验收留出余量；生产默认值、
   协议与实现不变。
3. 显式捕获完整错误；先证明 hook 已到达并记录 PID，再检查 isolated 分类、严格错误正则和
   从 hook 时刻计算的上界。若错误类别意外，直接展示完整 message。
4. 不提交、不推送、不创建 PR；完成后以未提交 diff 交付审阅。

## 验证边界与后续事项

本轮重复执行没有观察到遗留 supervisor，但现有 `onDrained` 测试 hook 只暴露 PID/PGID，
不暴露与原子进程生命周期绑定的强句柄。PID/PGID 可复用，且 macOS 当前进程身份只有秒级精度；
因此本轮不能以弱身份相等为依据追加兜底终止，否则会引入误杀无关进程的风险。Issue #155 单独
跟踪强生命周期观察与安全清理能力；在其完成前，不把“重复运行未观察到残留”表述为强身份清理证明。

## 黄金原则逐项对照

### 1. 先定义可证伪的完成合同

- **适用性**：适用。上表逐项给出通过证据与失败观察。
- **裁决**：以 hook 到达、错误类别、安全文件和重复执行结果共同定义完成，不以单次绿色代替。
- **验证**：定向单次、至少 30 次独立重复、相关 workspace-safety 测试与完整 diff 核对。

### 2. 生成方不得给自己签发通过

- **适用性**：适用。测试结果必须由 Vitest 机械断言，而不是修改者自述。
- **裁决**：先绑定真实 hook/PID，再检查完整错误与落盘事实；不接受被截断日志推断出的宽松类别。
- **验证**：保留严格正则和全部安全断言，失败时输出完整 message。

### 3. 自治范围扩大时同步增加防线与可逆性

- **适用性**：不适用。本次不扩大 Agent、命令、合并、部署或删除权限，只校准测试。
- **裁决**：生产行为保持不变；改动仅为两份可直接撤销的文本文件。
- **验证**：`git diff --name-only` 必须只有计划与目标测试。

### 4. 原生执行优先，差异只在控制平面

- **适用性**：不适用。本次不新增 runner、平台适配或执行能力。
- **裁决**：继续使用 Node、POSIX signal 和 Vitest 现有测试路径，不建立替代实现。
- **验证**：生产文件与跨平台合同零改动。

### 5. 以假绿率和失败恢复衡量价值

- **适用性**：适用。这是 CI 真实时序歧义，风险是用例未实施题名中的故障也参与裁决。
- **裁决**：将 hook 到达事实固化为前置断言，并用重复运行衡量误红率；不接受 receipt/quarantine
  类别来制造假绿。
- **验证**：至少 30 次独立成功，并运行相关 workspace-safety 测试确认没有旁路影响。

## 实施顺序

1. 修改目标用例的事实记录、错误捕获、测试预算和相对时间上界。
2. 运行定向用例一次，再至少 30 次逐轮独立运行。
3. 运行相关 workspace-safety 测试，核对格式、差异范围与工作树状态。
