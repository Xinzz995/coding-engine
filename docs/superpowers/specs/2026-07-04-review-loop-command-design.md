# 设计文档：/review-loop 审查命令 —— 循环产物的人审辅助包

- 日期：2026-07-04
- 状态：已批准
- 来源：0.7.0 闭环验证的关键教训「validator 也是 agent，会共谋假绿——引擎产物必须人审后合并」；审查线为 ponytail 评估的 P2 借鉴项（tag 化一行式格式）；改动导读层借鉴 beginner-learning-code 的贴码讲解法（先做什么/数据怎么流/哪部分是核心）

## 1. 背景与目标

0.7.0 的真实案例：引擎 4 story 零重试全绿，人审却抓到 validator 漏掉的 bug（doctor 索引提取把 AGENTS.md 描述列内嵌的 gitignored 路径当索引项——本机全绿、CI 干净检出假失败，fix 6c3c6bd）。结论固化为流程：**分支跑完 → 人审 → fix → 合并 → 收口**。人审的瓶颈是理解速度（当时靠人肉通读 288 行新代码）。

本轮把「人审」环节工程化：新增 `/review-loop` 命令，在合并前为人产出一份结构化人审包，降低理解成本、用系统化嗅探清单提高检出率。**它是人审辅助，不是人审替代**——审查 agent 同样可能漏，包是加速器不是保险箱，人保持最终裁决。

## 2. 已锁定的决策

| 决策点 | 结论 |
|---|---|
| 形态 | 审查命令 + 引擎完成提示（不做循环内自动 Reviewer、不做引擎自动触发——先以最小形态积累真实经验） |
| 审查范围 | 双维度：正确性（教训直接来源）+ 过度工程（顺带验证 0.8.0 builder 阶梯被遵守）；ponytail-review 只借格式不借「排除正确性」的范围 |
| 人审包构成 | 三层：改动导读 / 发现清单 / 风险聚焦；AC 覆盖问题以 test-gap tag 按异常报告，不做全量对照表 |
| 命令名 | `review-loop`（与引擎叙事一致，完成提示里与 /compound-docs 对仗） |
| 产物去向 | 直接呈现在对话里，不落盘报告文件 |
| 版本 | 0.9.0 minor（新命令，先例 0.6.0 compound-docs） |
| validator.md | 不改 |

## 3. 定位与触发

- 落点 `commands/review-loop.md`（仓库根 commands/ 唯一源，各工具经既有 manifest 机制获得）。
- 触发：循环全部通过后、**合并默认分支之前**，人手动运行。
- 只读纪律:不修代码、不改文档、不写 `.workspace/`。发现问题列出来，修不修由人决定。
- 引擎完成提示（`src/engine/loop.ts:116`）改为引导正确顺序：

  > 💡 全部 story 已通过。建议先运行 /review-loop 审查本轮产物（人审后合并），再用 /compound-docs 收口沉淀。

  这是本轮唯一 src 代码改动，TDD 更新 loop.test.ts 中既有的完成提示断言。

## 4. 输入与降级

- git 取证基线同 compound-docs：`merge-base(origin 默认分支, HEAD)..HEAD` 的 log 与 diff。
- `.workspace/` 存在时增强：`prd.json`（story 列表与 acceptanceCriteria，导读按 story 组织）、`state.json`（notes 中的 [需求冲突]/失败历史）、`progress.md`（理解实现意图；**不作为验证依据**）。
- 降级：无 `.workspace/` → 纯 git diff 审查，导读按提交组织，test-gap 降为「测试覆盖疑点」（无 AC 可对照）；与默认分支无分叉 → 明示无可审内容并结束。
- 排除：lock 文件、构建产物、依赖目录的 diff 不进入审查与行数统计。

## 5. 人审包三层格式

**层 1 改动导读**（按 story 组织；降级时按提交组织；每项 3-6 行）：
- 改了什么：核心逻辑位置以 `file:line` 给出
- 数据怎么流：输入 → 处理 → 输出，贴着代码讲，不写空泛概念
- 与其他 story 改动的接缝（共享文件/函数）

**层 2 发现清单**（一行一发现）：

格式：`<file>:<line> <tag> <缺陷/砍什么>。<失败场景/替代方案>。`

- 正确性族（在前，按严重度排序）：
  - `bug:` 逻辑错误
  - `assume:` 环境隐含假设（gitignored 文件被业务逻辑读取、绝对路径、本机特有状态——0.7.0 的「本机绿 CI 假失败」即此类）
  - `test-gap:` 测试未真正覆盖 AC（断言与 AC 不对应、测了 mock/测了自己）
  - `edge:` 边界缺失（空串/0/负数/非法格式）
- 质量族（在后，按可砍行数排序）：`delete:` `stdlib:` `native:` `yagni:` `shrink:`（语义同 ponytail-review：死代码/标准库已有/平台原生已有/单实现抽象/同逻辑更短）
- 质量族末行：`net: 约可减 N 行`
- 空结果语：正确性族「未发现正确性问题（不等于没有——人审仍是最终裁决）」；质量族「无可砍项」
- 清单末行总结：`审查结论：建议合并前处理 N 项正确性发现`（是建议不是门禁；N=0 时写「未发现需合并前处理的问题」）

**层 3 风险聚焦**（top 2-4 处）：
- 建议人重点细看的文件/逻辑，以及为什么（环境假设密集、测试薄弱、触碰共享路径、复杂度陡增）
- 用怀疑式提问句引导人审视角，如「CI 干净检出时这段还成立吗？」「这个测试在空仓库上还过吗？」

## 6. 审查纪律（命令硬性约束）

1. **独立复核**：不得以「validator 已通过」「progress.md 说完成」为证据；验证要独立重推（读代码、跑检查、必要时实际执行）。
2. **假绿嗅探清单**（逐项执行的具体动作）：
   - 业务逻辑读取的每个文件/路径：在干净检出（CI）环境下存在吗？被 gitignore 了吗？
   - 每条 acceptanceCriteria：找到对应测试断言；断言真的在测这条 AC 吗？
   - 新增外部输入（CLI 参数、文件内容、环境变量）：空串/0/非法格式会怎样？
   - 修改共享函数时：所有调用方都核对过了吗？
3. 质量发现只列出不阻塞；正确性发现给严重度但最终裁决归人。
4. 只读不改；不写任何文件。
5. 目标项目自身是 harness 工具时的自指豁免同 compound-docs 约定。

## 9. 非目标（YAGNI）

- 不做循环内每 story 自动 Reviewer（形态 B）与循环后引擎自动触发（形态 C）——等命令形态积累真实经验
- 不落盘审查报告文件（.workspace/review.md 等）
- 不自动修复发现（含 --fix 类参数）
- 不做 PR/平台集成（gh pr comment 等）
- 不做自定义审查范围参数（`<base>..<head>`）——默认 merge-base 语义先跑
- 不改 validator.md
