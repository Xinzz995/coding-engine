# 设计文档：builder 反过度工程阶梯与取舍标记收账

- 日期：2026-07-04
- 状态：已批准
- 来源：ponytail（github.com/DietrichGebert/ponytail）评估的 P1 借鉴项；上游脉络见 P0（版本防线三道 + 常态 CI，已随 7a8868e/2959c58 落地）

## 1. 背景与目标

AI 生成代码的通病是过度复杂化（ponytail 实测其阶梯约束平均减少 54% 代码量且 100% 保留安全守卫）。coding-x 的 builder 指令目前只有一句抽象的「保持更改专注且最小化」，agent 不可执行。本轮把它扩成可执行的生产版细则，并为「有意识的简化」建立标记与收账闭环，防止 "later means never"。

目标：
1. builder 写码前有明确的决策顺序（阶梯），产出更克制的代码——也降低人审负担（0.7.0 教训：产物必人审，代码越少越好审）。
2. 修复类改动修根因不修症状。
3. 有已知上限的简化留下机器可收账的标记，收口时汇总成账本。

## 2. 已锁定的决策

| 决策点 | 结论 |
|---|---|
| 收账归属 | `/compound-docs` 收口时收账（不做 doctor 门禁、不做独立命令——标记体系先跑起来，有真实积累再议更硬防线） |
| 标记词 | `取舍:`（语义准、grep 零误报、中文与项目语言一致）；格式 `// 取舍: <当前上限>，<升级触发条件>` |
| 版本 | 0.8.0 minor（新增用户可感知的约定体系，向后兼容） |
| builder.md 写法 | 紧凑集成进「质量要求」区（每轮循环注入，长度即 token 成本），不开独立大节 |
| validator.md | 不改——已锁定「验收只以 acceptanceCriteria 为准，不因风格/品味追加失败项」（validator.md:64），取舍标记不会被误打回 |

## 3. builder.md 改动（唯一改动点：「质量要求」区）

现有 4 条中「保持更改专注且最小化」被阶梯条吸收删除，扩成 7 条：

```markdown
## 质量要求

- 所有 commits 必须通过项目的质量检查（typecheck、lint、test）
- 不要提交损坏的代码
- 遵循现有的代码 patterns
- **写码前按序自查，停在第一个成立的台阶**：本项目已有的 helper/util/pattern 能复用吗 → 标准库能做吗 → 运行时/平台原生特性能覆盖吗 → 已装依赖能解决吗 → 都不能，才写只满足当前 acceptanceCriteria 的最小实现
- 不为「以后可能用到」预留结构：不写只有一个实现的接口、没人读的配置项、只有一个调用方的抽象层；只调用一次的函数优先内联（除非内联后明显更难读）
- **绝不简化掉**：信任边界的输入校验、防数据丢失的错误处理、安全措施、测试；acceptanceCriteria 要求的内容一律不打折
- 修复类改动（含 Validator 打回的重试）修根因不修症状：动手前 grep 你要改的函数的所有调用方，把修复放在共享路径上——只修报告提到的那条路径会留下其他调用方继续坏
- 选择了有已知上限的简单实现时，就地留取舍标记：`// 取舍: <当前上限>，<升级触发条件>`（如 `// 取舍: 全局锁，吞吐量成瓶颈时改按账户锁`）。只标真实的取舍决策，不是每处简化都标
```

设计要点：
- 阶梯从「复用本项目已有」起步。ponytail 的第 1 级「这个任务该存在吗」不移植——builder 无权质疑 PRD，需求取舍属于 prd-generate 与人。
- 「绝不简化掉」清单与 TDD 纪律咬合（测试在清单内），区别于 beginner-learning-code 那类教学向 skill（其默认砍测试，与本引擎生产纪律冲突，评估结论为不采用）。
- root-cause 条款同时覆盖 bug 类 story 与 validator 打回重试两个场景，故放全局质量要求区而非 step 4。

## 4. compound-docs.md 改动（收账，两处）

**4a 「### 2. 交叉取证」末尾追加一段**：grep 全仓库 `取舍:` 标记（跳过依赖目录与构建产物），并说明——取舍标记是**收账对象，不是沉淀候选**（防止被当成经验写进项目 docs）。

**4b 「### 6. 交付说明」追加「取舍账本」要求**：
- 每处标记一行：`<文件>:<行号> <简述>。上限：<...>。升级条件：<...>`
- 缺升级触发条件的行标 `[无触发条件]`，并提请用户补全或处理（这类标记最易烂掉）
- 末行汇总：`共 N 处取舍，M 处无触发条件`
- 仓库无标记时一句「无取舍债务」
- 账本只进交付说明报告，不写入项目文档、不落盘新文件

## 5. README 同步

builder 工作原理段落与 /compound-docs 介绍处各补一句：取舍标记约定、收口时汇总账本。具体插入点在实施计划中 grep 定位。

本仓库自身的 `docs/patterns.md`、`docs/architecture.md`、`AGENTS.md` 不动：无模块结构变化；`取舍:` 约定将通过下次引擎真实运行与收口自然进入目标项目文档。

## 6. 测试与验证

纯指令/文档文本改动，无 src 代码，无单测新增：
- grep 断言：关键词一字不差取自正文（SDD 教训：不得用计划叙述词）
- `npm run build` 后 `dist/instructions/builder.md` 包含新质量要求区（assets → dist 拷贝链路验证）
- 延迟验证项（不阻塞本轮）：下次引擎真实运行观察 builder 是否正确使用取舍标记、收口是否正确出账本

## 7. 执行方式与发版

- 主会话直接实施（3-4 任务的轻量计划），不派 subagent、不跑引擎循环
- 发版 0.8.0：`npm version 0.8.0 --no-git-tag-version`（version 钩子自动同步三个插件清单与 lock——P0 三道防线首次全链路实战）→ release 提交 → tag 推送 → CI 发布
- 提交说明中文（conventional 前缀保留英文）

## 8. 非目标（YAGNI）

- 不做 doctor 的取舍标记格式门禁（等标记有真实积累）
- 不做独立 /debt 命令
- 不改 validator.md
- 不把 ponytail 本体整合进插件（定位正交，用户可并行安装）
- 不在本轮做 ponytail-review 式人审包（属 0.8.x 之后的审查线候选，其 tag 化格式已存为设计输入）
