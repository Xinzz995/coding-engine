# 架构地图

## 双形态

同一仓库两条产品线，互不依赖：

- **npm 引擎**：`src/` → tsup → `dist/`，`npx coding-x` 运行 Developer ⇄ Validator 循环
- **多工具插件**：根 `skills/`、`commands/`、`hooks/` 为唯一源，`.claude-plugin/`、`.cursor-plugin/`、`.codex-plugin/`、`.agents/` 只放瘦清单或宿主所需的单一接线

## 分层与依赖方向

cli → quality + engine + workspace-safety。run 在 loop 入口取得 session；agent/gate/tdd/review 只通过
session coordinator 启动子进程，state/evidence/guard/report 只通过 session writer 写入。apply-prd、
repair 与 review-decision 各自使用固定产品动作，不能把路径或写权限交给调用方；recover/resume 只
消费已落盘恢复身份。doctor、status 与 dashboard 共用只读 safety classification。report 被 cli 与
loop 调用：手动入口获取短 session，自动入口借用 run session。`assets/` 与共同 hook 脚本构建时
拷进 `dist/`；CLI 以自身 `import.meta.url` 定位构建后的指令目录。`templates/`、`skills/`、`commands/`
与宿主 hook 配置只随插件仓库分发。

## 数据流

项目知识也分冷热生命周期：`/compound-docs` 默认只对本轮相关 active 文档做沉淀与增量熵 GC，用户显式要求全量时才逐条审计 patterns/glossary/architecture/golden-principles/prompt-writing；任务型文档先以证据收尾 status，再在用户明确授权物理归档后镜像原相对树移入 `docs/archive/`。冷档案继续由 doctor 检查 frontmatter 与相对链接，但不参与 updated 新鲜度，也不进入日常实现/沉淀上下文。

`.coding-x/quality.json` 是项目检查唯一人工维护来源。prd-to-json 用 doctor 取得规范化摘要和结构化
派生快照，在系统临时目录生成候选与绑定请求，再调用 `workspace apply-prd`；命令在短 session 内
重核 Git/质量绑定、重跑已确认的 TDD 基线，并用固定 mutation 归档旧运行、应用 PRD/state/progress。
skill 不直接写 workspace。正式 run 要求精确版本、摘要和快照一致；builder 只实现一个 story 并
留下 `passes=true` 候选。契约检查与 TDD 门禁通过后，引擎才把 story ID、有序 AC 快照/hash、一次性
request ID 与 Git HEAD 注入 Validator；Validator 只写逐 AC claim，引擎核对后才写状态或签发
`validated=true` 及提交绑定凭证。后续提交或 Story ID/有序 AC 变化会撤销验收而保留实现候选，待完整
机械检查与 Validator 重新确认；全部非 blocked Story 的精确凭证集合还会绑定最终 Review，并在模型
前后、落盘和 loop 接受边界重复核验（ADR-009、013、015、017、018、020、021）。

项目检查、TDD 与 Validator 组成绑定同一 Git HEAD 的验收链。引擎在各阶段开始和结束边界重读
HEAD；变化或不可读时立即停止且不增加重试。若命令已经结束，evidence 保留真实执行事实，但以
`accepted=false` 明确表示它没有进入裁决；同轮 iteration 另存通用中止阶段与预期/实际身份，
status/report 不能把该命令显示为普通通过或普通失败。本地 evidence 只用于诊断，不是 GitHub
共享交付证明。

coding-engine 的 GitHub 与暂存流程不运行候选版本的完整 doctor。它们运行仓库机械健康检查，
只验证文档、契约结构和契约生成文件；完整 doctor 继续拒绝候选版本与固定版本不一致。
首次稳定自举实际使用 0.33.1（0.33.0 已被 npm 判定不可复用），发布前由机械检查和 owner
人工 Bootstrap 裁决，不声称取得正式本地 Review；发布后通过独立 Policy PR 固定 0.33.1，
正式自托管才开始。因此首发阶段的远端总闸成功不表示候选取得正式裁判资格（ADR-018）。

发布链把“构建候选”和“取得 npm 暂存身份”拆成两个独立工作流与权限域。前者执行完整项目
代码但没有发布身份，产物先供三个项目 Dogfood；后者由维护者选择已经验证的候选运行，回读
其来源、成功状态与当前 `main`，只下载固定候选、重建不执行脚本的包目录并核对摘要，OIDC
只能执行 `npm stage publish`。维护者 2FA 批准后仍需三个项目从 registry 验证精确版本，人工
移动 `latest` 后才创建标签；标签固定所选暂存任务、npm stage ID 与候选摘要，标签工作流沿
stage 证据找到原候选运行，分别对账后创建不可变 Release（ADR-018、019）。

workspace 是运行边界：`workspace-safety.json` 与永久 `engine.lock/` 绑定目录身份；活动 writer 位于
`engine.lock/lease/`。progress、evidence、Validator IPC、截图、Review 与报告的每次修改都属于当前
owner 或一个明示 delegated child。Agent stdout/stderr 实时 tee，异常时只留有界尾部；operation
只有 containment 清空且 delta 合法后才结算。父进程崩溃、终止失败、越界变化或未完成 mutation
保留隔离，由 `workspace recover|resume-mutation` 显式处理，不做 stale 自动接管。PRD guard 冻结
运行期需求并通过 writer 恢复；自动报告沿用冻结快照，手动报告读取磁盘但同样持短 session。
`/review-loop` 只生成临时最小请求，由 review-decision 入口在开始和提交前重核完整 Review binding、
HEAD、PR 意图、Runner 与 Issue；它绑定请求中的操作者标识，并由引擎签发 binding 摘要、head 与时间。
旧版非空 workspace 只有 status/dashboard 可以直接只读回看；report 只能在已经完成新版安全初始化
的 workspace 内解释缺少 state 或旧形状 PRD，不能为旧 workspace 重新生成报告。正式写入入口拒绝
迁移非空旧 workspace；state 存在但损坏时所有展示面 fail-closed（ADR-007、008、014、015、016、017、021）。

全局模型目录声明 runner 可选择的 ID，项目 `prd.json.models` 保存 runner 与五项映射；preflight 只在显式模型策略可能被调用时检查目录成员，loop 再按 difficulty、escalated 与 CLI 覆盖解析本轮模型，并把实际命中写入 evidence。目录是静态允许清单，不证明 provider、认证、配额或网络实时可用；runner-default 与已收敛 workspace 跳过目录（ADR-011、012）。
