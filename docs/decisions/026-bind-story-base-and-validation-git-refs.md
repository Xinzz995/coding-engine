# 026. Story 验收必须绑定固定起点与验证 Git 引用

## 背景

现有 Validator request、持久凭证和当前性判断只绑定最终 Git HEAD。真实 0.36.0 RC1 自托管中，
同一验收条件第一次因目标文件在父提交中已存在而失败；随后历史先删除文件、再重新加入，第二次验收
只观察最后一次提交并通过。整个 PR 的 Final Review 仍会观察默认分支到最终 HEAD 的完整变化，但单个
Story 凭证无法回答“这个 Story 从哪个提交开始”，也不能把重试固定在同一比较范围。

Issue #210 同时证明，精确提交的干净检出虽然保留提交对象，却不建立 `origin/main` 等验证命令依赖的
引用。相同质量合同在开发仓库可运行、在 Validator 检出不可运行，结局取决于 Validator 是否逐字执行
项目命令，破坏确定性。

## 决策

1. 每个 Story 第一次进入实现轮时，引擎把当时的完整 Git HEAD 保存为 Story 固定起点。该字段与
   `validated`、凭证和不可验证标记一起归引擎独占；Builder、Validator 删除、替换或补写都必须被恢复
   并留痕。同一 Story 的失败、重试、恢复和最终重验都沿用同一起点。
2. 已存在实现候选但没有固定起点的旧 workspace 不从 `HEAD^`、最终 Review、evidence 或当前文件
   反向猜测起点。它保留候选但返回不可验证，要求从明确基线建立全新 workspace。
3. Validator 协议升级，request、result 和持久凭证同时绑定 Story 起点、最终 HEAD 和引擎在干净检出
   中计算的整段 Git 变化摘要。Validator 必须检查 `Story 起点..最终 HEAD`，不得用 `HEAD^` 或自行
   选择比较范围。旧协议结果不能进入新控制流；旧凭证继续可读但自动失效。
4. 引擎只在 Story 起点是最终 HEAD 的祖先时生成变化摘要。删除后重加、历史重写、起点不可达或摘要
   漂移都失败关闭，不签发凭证。变化摘要只定义本次 Story 验收的完整观察范围，不宣称每个文件都由
   该 Story 独占；整个 PR 的最终范围仍由 Final Review 裁决。
5. Story 验收启动时，受管 Git 读取质量契约所声明默认分支的本地远端跟踪提交。该完整提交与引用名
   进入验证环境身份；干净检出仅建立对应的只读等价引用，例如
   `refs/remotes/origin/main -> <固定提交>`。引用缺失、不是完整提交、运行期间漂移或被改写都不可验证。
6. Final Review 已从 GitHub 固定 PR base SHA；其干净机械检出使用该 SHA 建立相同的默认分支引用，
   不依赖开发仓库中可能漂移的本地引用。

## 信任边界

- 变化摘要由引擎在已核对的干净检出中生成，绑定完整 Git 对象范围；它不是作者身份或密码学签名。
- 固定 Story 起点防止通过改变“最后一个父提交”缩窄观察范围，但不会自动判断某项变化是否符合产品
  意图；逐项 AC 仍由 Validator 检查，整个 PR 仍由 Final Review 与远端规则共同裁决。
- 本地远端跟踪引用是运行输入，不等于 GitHub 当前事实。Story 验收会把它固定并持续复核；最终 Review
  仍以 GitHub PR base 为远端权威。
- 同权限恶意进程仍可能修改 workspace 文件；本决策沿用现有引擎所有权恢复和受管观察边界，不虚构
  本地密码学隔离。

## 被否方案

- **默认使用 `HEAD^`**：提交拆分、删除重加或历史整理会改变验收范围，正是本次真实假绿来源。
- **只依赖整个 PR 的 Final Review**：它能裁决整体交付，却不能让逐 Story 凭证诚实表达自己的范围。
- **从旧候选当前状态猜起点**：无法区分原始任务基线、首次实现提交和恢复提交，会补造并不存在的证据。
- **把 `origin/main` 指向候选 HEAD**：会让增量检查看到空差异，掩盖本应检查的 PR 变化。
- **复制来源仓库全部 refs**：扩大输入与漂移面；只建立质量合同所需默认分支引用即可。

## 后果

- 旧 v3 Story 凭证和缺少固定起点的旧候选不能继续表示当前通过，必须在新 workspace 中重新验收。
- Validator 协议、凭证 schema、状态读取、evidence、报告和测试夹具需要同步升级。
- 干净检出身份升级；旧环境摘要自动失效。
- 默认分支本地跟踪引用缺失时，正式运行会在 Agent 启动前给出明确修复提示，不再等到 Validator 内部
  偶然失败。
- 0.36.0 候选必须从包含本决策的新 `main` 重新构建；既有 RC1 不能继续提升发布。
