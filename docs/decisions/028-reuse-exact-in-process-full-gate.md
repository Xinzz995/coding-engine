# 028. 最终 Review 只复用同一进程内输入完全相同的全量检查

## 背景

每个 Story 已由引擎在干净检出中运行完整质量契约；全部 Story 收敛后，最终 Review 又运行同一组
命令。长测试项目因此把大量时间花在重复证明上。直接缓存“绿色”又会把旧提交、旧默认分支、旧规则
或不同验证环境带进最终结论，增加假绿风险。

## 决策

1. 引擎只在全量契约检查全部通过，并再次确认源 HEAD、干净检出和状态所有权没有变化后，创建一次
   内存证明；失败、部分执行、旧式命令列表和测试注入结果都不能创建证明。
2. 证明绑定精确 head、默认分支基线、完整质量契约摘要、系统平台、干净检出协议以及检查命令可见的
   全部 Git 引用。最终 Review 完成自己的 PR/base/规则预检后，重新计算同一输入身份；逐字段完全
   相等才复用，否则按原路径重建干净检出并重新运行。
3. 证明不落盘，不跨进程、不跨继续运行。TDD 基线带来额外可见引用时，最终 Review 输入不同，因此
   保守地重新运行；TDD 门禁本身始终独立执行。

## 后果

- 常见的无 TDD 额外引用项目可以去掉 Story 收敛到最终 Review 之间的一次完整重复检查。
- 默认分支推进、规则变化、系统变化、额外引用变化或进程重启都会自然失去复用资格。
- 复用减少的是相同输入的重复执行，不减少 Review、远端总闸或 Validator 的职责。
