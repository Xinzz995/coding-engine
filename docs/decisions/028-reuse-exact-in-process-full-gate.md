# 028. Validator 与最终 Review 复用同一进程内输入完全相同的全量检查

## 背景

每个 Story 已由引擎在干净检出中运行完整质量契约；随后 Validator 会因 Story 中复制的 test、build、
typecheck 类 AC 再运行相同命令，全部 Story 收敛后最终 Review 又运行一次。Python 多包候选实证表明，
重复不仅增加耗时：Validator 的断网隔离还可能让已经通过的 wheel 构建因再次下载依赖而变成“无法
验证”。直接缓存“绿色”又会把旧提交、旧默认分支、旧规则或不同验证环境带进最终结论，增加假绿风险。

## 决策

1. 引擎只在全量契约检查全部通过，并再次确认源 HEAD、干净检出和状态所有权没有变化后，创建一次
   内存证明；失败、部分执行、旧式命令列表和测试注入结果都不能创建证明。
2. 证明绑定精确 head、默认分支基线、完整质量契约摘要、系统平台、干净检出协议、检查命令可见的
   全部 Git 引用，以及本平台实际执行的检查类别、ID 与模块。证明作为 validation request v2 的可选
   引擎字段交给 Validator：只对清单明确覆盖的机械 AC 禁止重跑并引用该证明；代码语义、范围、业务
   边界和未列出的能力仍由 Validator 独立验证。
3. `prd-to-json` 不再给每个 Story 强制追加通用 `Typecheck passes` 或 `Tests pass`。顶层质量契约已经
   承担机械门禁；来源 PRD 明确写出的机械 AC 仍保留，并由 Validator 对照证明清单。
4. 最终 Review 完成自己的 PR/base/规则预检后，重新计算同一输入身份；逐字段完全相等才复用，否则
   按原路径重建干净检出并重新运行。
5. 证明不落盘，不跨进程、不跨继续运行。TDD 基线带来额外可见引用时，最终 Review 输入不同，因此
   保守地重新运行；TDD 门禁本身始终独立执行。
6. ADR-030 启用检查 `paths` 后，“完整”指当前可信 Git 变化适用的完整检查集合，不再等同于契约中
   所有命令。按范围证明额外绑定变化起点、变化摘要和有序检查 ID；未知范围回退全量。旧的全量
   证明语义保持不变。

## 后果

- Validator 不再把引擎刚完成的相同适用项目检查再跑一遍；语义复核职责不减少。
- 常见的无 TDD 额外引用项目也可以去掉 Story 收敛到最终 Review 之间的一次完整重复检查。
- 默认分支推进、规则变化、系统变化、额外引用变化或进程重启都会自然失去复用资格。
- 复用减少的是相同输入的重复执行，不减少 Review、远端总闸或 Validator 的语义判断职责。
