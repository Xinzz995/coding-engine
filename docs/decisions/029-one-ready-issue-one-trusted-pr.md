# 029. 首个任务入口固定为一个 ready Issue 对应一个可信 PR

## 背景

coding-x 已有强验收和交付边界，但没有足够小的任务入口。用户仍要手工准备 PRD、分支、PR、运行和
状态同步；路线若先扩展轮询、队列和更多 Agent，只会把尚未闭合的一次任务放大成调度平台。

## 决策

1. 首个入口是维护者显式执行 `coding-x issue run <编号> [runner]`。它只接受开放、非 PR、当前带
   `ready-for-agent` 标签，并按受管模板填写目标、非目标、列表式验收标准和风险的 Issue。
2. 运行身份由仓库、Issue 编号、当前 ready 标签事件和 Issue 正文摘要共同确定；分支固定为
   `codex/issue-<编号>`，源 PRD、workspace 和草稿 PR 均由该身份确定。重复命令只继续同一分支、
   workspace、状态评论和 PR；正文或 ready 事件变化不能借用旧运行。
3. 入口可以创建/切换该唯一分支、提交源 PRD、推送当前分支、创建草稿 PR、更新一条 owner Issue
   评论，并在可信完成后把草稿标为 ready。它不轮询、不排队、不合并、不发布，也不处理其他 Issue。
4. 本地提交推送后命令以等待远端状态停止；维护者稍后运行同一命令继续。运行、等待、失败、当前
   head、PR 和 Review 证据都写回同一 Issue 评论。入口在切分支、推送和创建 PR 之前先写“准备中”；
   首次建 PR 或工作区准备失败都更新这条评论，PR 成功后同一评论原位升级为完整状态。引擎返回后
   必须再确认 PR 仍开放、目标分支和最新提交未变，才能标记可信。续跑若已有正式最终 Review，先用
   受管 status 重新核对提交、基线、PR 意图、需求、规则、契约、Runner、验收凭证和裁决；全部仍
   当前时只刷新 GitHub 状态，不重跑 Builder、Validator、项目检查或 Reviewer。当前性缺失或变化则
   回到完整路径；准备标记可信前再次执行同一受管观察，刷新期间或刷新返回后的标签与上下文变化都
   保持未就绪，不能使用旧观察放行。
5. 首要效率指标从当前 `ready-for-agent` 标签事件开始，到当前 PR head 同时取得正式本地结论和
   远端总闸结论为止。最终评论同时展示总时间、实际命令运行时间和其余等待时间；重跑不重置起点。

## 被否与暂缓

- 暂缓自动轮询、多任务队列、GitLab/Qoder 全覆盖和更多 Agent 编排。只有单任务闭环的恢复失败率、
  假绿率和总时间有稳定实测后，才重新评估这些能力。
- 不以 Agent 运行时间代替总时间；CI 和人工继续等待正是用户真实感受到的交付延迟。

## 后果

- 当前路线优先优化一次真实任务的总交付时间，而不是任务吞吐或并发数。
- 单用户 owner 是本阶段治理边界；团队派单、权限分层和队列公平性不在本决策承诺内。
