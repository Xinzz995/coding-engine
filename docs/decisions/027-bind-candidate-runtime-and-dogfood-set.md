# 027. 发布许可必须绑定候选实际运行内容与三仓证明集合

## 背景

旧候选证据只记录压缩包摘要。三仓 Dogfood 再分别抄写摘要，暂存任务只确认候选构建成功；维护者
仍要人工判断三仓是否确实使用同一候选。更深的问题是发布包过去会从包外加载 `jsonrepair`：主包
文件即使完全匹配，实际执行内容仍可变化，因此“候选摘要”尚不是运行身份。

## 决策

1. 候选证据升级为 schema 3，同时绑定压缩包摘要、候选来源运行和 npm 包内全部发布文件的路径、
   大小、内容摘要与文件树摘要。候选 CLI 只有在启动时从自己的真实安装目录逐文件复核通过，才能
   把候选身份写入 Shadow Story 凭证和最终证明。
2. 唯一运行库 `jsonrepair` 固定为精确版本并并入 `dist`；发布包不再从包外加载运行代码。这样候选
   文件树才覆盖 coding-x 的执行内容，而不是只覆盖入口外壳。
3. 成功的候选 Shadow 运行必须同时满足 Story 凭证当前、最终 Review 通过、PR 最新提交的远端总闸
   ready，才在 workspace 生成 `candidate-proof.json`。证明同时保存当时的默认分支提交和全部必需
   检查。显式 `candidate publish-proof` 再核对当前仓库、owner、分支、PR、head、base 和可合并状态，
   把唯一证明评论发布到该 PR。
4. 发布政策固定 coding-engine、Go、Python 三个试点。暂存工作流先读取三个指定 PR 及 owner 证明
   评论，并重新读取每个 head 的检查结果，逐项核对唯一仓库、默认分支、当前 head/base、可合并状态、
   候选身份、证明摘要和必需检查；三份都通过后才进入需要人工批准的 npm environment。批准后的
   任务会再次读取三仓并要求结果与批准输入完全一致，随后才取得 npm 身份。
5. 证明不是密码学签名，也不证明真实业务采用。它证明的是固定 owner 在三个固定公开试点上，针对
   同一候选和当前 PR head 完成了当前项目已有的验收链。

## 被否方案

- 只让三仓复制 tarball SHA：不能证明实际 CLI，也不能阻止复用旧绿色结论。
- 批准时人工打开三个 PR：无法失败关闭，也无法被后续发布任务重放核对。
- 直接信任 Actions 成功：外部仓的普通 CI 不知道候选身份，成功状态不能替代候选证明。
- 只锁定外部运行依赖版本：降低解析漂移，但仍不能证明本机实际加载的依赖字节。

## 后果

- 旧 schema 2 候选、无文件树身份的 Shadow 凭证和人工三仓说明不能进入新暂存流程。
- 任一候选运行文件被替换、经过链接、缺失，或三仓少一份/错仓/错 head/错 base/错 owner、检查被
  重跑为失败、PR 在批准期间变化，都会在 npm OIDC 之前停止。
- npm 暂存仍需人工批准；本决策没有授予自动批准、发布、移动标签或合并 PR 的权限。
