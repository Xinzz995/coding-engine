# 010. models 具名档案：配置一次，任何 agent 工具定位自己的模型名

> 2026-07-21 起由 ADR-011 取代。用户明确不需要跨 runner 复用同一配置，`profiles` 不再是当前目标。

## 背景

ADR-006 确立模型路由「透传不映射」，其中一条理由是「一次 run 只有一个 kind，可移植性服务的场景不存在」。2026-07-20 用户实测反馈该理由不完整：`prd.json` 作为配置载体跨运行存活，同一工作区完全可能先后用不同 agent 工具（claude/codex/cursor…）跑引擎，而模型名对工具不可移植——claude 的 `sonnet`/`fable` 传给 codex CLI 就是错名，扁平 `models` 段让「换工具跑」必须改配置文件。

首版方案曾做成「按工具分段」（`models.claude = {…}`、`models.codex = {…}`，键=工具名），用户否决：配置主语变成工具、每个工具各持一套独立配置，新增工具要整段补写，story 级覆盖也随工具膨胀。需求确认为：**配置一次模型，之后任何工具都可使用**（2026-07-20 需求讨论，用户拍板：档案形状 / 配置留 prd.json / 缺条目警告不失败）。

## 决策

`models` 新增可选 `profiles`——具名模型档案（档案名 → { 工具名 → 模型名 }）；阶段字段与 story 级 `model` 写**模型引用**，统一解析规则（`src/engine/models.ts` 的 `resolveRef`）：

1. 引用命中档案名 → 取当前运行工具（kind）的条目；**缺当前工具条目 → 该引用不生效 + 警告**（不传 `--model` 用该工具默认模型，不传比传错名诚实）。
2. 引用未命中任何档案 → 当字面模型名原样透传——旧扁平配置（`builder: "sonnet"`）零迁移，仍适合单工具场景。
3. 配置仍放 `prd.json`（随 prd-to-json 派生时人工确认，与 qualityChecks 同载体）。
4. 报告展示不知运行工具：阶段显示原始引用，档案表如实列出每工具条目（`readModelsSpec`）。

「透传不映射、validator 恒定、升级复用 retryCount」三取舍不变（ADR-006 其余部分继续有效）。

## 理由与备选

- **为什么档案在配置里而不是引擎内置映射表**：ADR-006 否决 tier 抽象的理由是引擎内置名单必然过时；档案由用户维护、放在自己的配置里，引擎依旧零模型名单——staleness 论据不适用。
- **为什么缺条目是警告而不是回落别的工具条目**：把 claude 的模型名传给 codex 是必错配置；与 ADR-006「名字写错由 agent CLI 立即报错」同一立场的保守面。
- **为什么工具键不限定枚举**：引擎当前只认 claude/codex，但档案条目键是不透明字符串——未来接入新工具（如 cursor）旧配置零迁移，未知键只是「非当前工具的条目」。
- **被否备选——按工具分段**（首版，`models.<kind>.<stage>`）：功能等价但配置主语错位（见背景），story 级覆盖需逐工具写名字，「一次配置」性质弱。
- **被否备选——角色优先嵌套**（`models.builder.<kind>`）：比分段直白，但新增工具仍要改每个角色行、story 级同样膨胀；档案形状把「工具 → 名字」的映射收敛到唯一位置。
- **被否备选——项目级独立配置文件**（跨 PRD 一次配置）：违反引擎零配置文件哲学（ADR-006 已否决一次），多一个真相源与 prd-to-json 确认环节脱节；用户拍板留 prd.json。

## 后果

- prd-to-json 派生环节新增确认面：问清用户实际用哪些工具跑引擎，档案里只写确认过的工具条目（skills/prd-to-json/SKILL.md 已同步）。
- 字面名与档案名共享命名空间：档案名恰好撞上真实模型名时字面透传不可达（档案优先）——档案名用语义词（fast/strong）自然避开，不做保留字校验。
- 旧扁平 PRD 零迁移；新档案 PRD 在 0.22.0 及更早引擎上，阶段引用（如 `"builder": "fast"`）会被当字面模型名传给 agent CLI 快速报错——跨版本混跑可从 agent stderr 直接发现，无静默错配。
- 面向用户的行为新增（配置形状扩展）随下次发版升 minor（硬约束 5）。
