# 规划一个新任务

## 功能: $ARGUMENTS

## 使命

通过系统化的代码库分析、外部调研和策略规划，把一个功能需求转化为**完整的实现计划**。

**核心原则**：这个阶段不写代码。目标是产出一份上下文充分、可直接执行的实现计划，让 AI 代理能够一次性高成功率落地。

**关键理念**：上下文为王。计划必须包含实现所需的全部信息，包括模式、必读文件、文档、验证命令等，让执行代理第一次尝试就能成功。

**输入与链条位置**：输入可以是原始功能描述，也可以是已拍板的对齐稿（`docs/prds/align-*.md` 业务口径、`docs/prds/tech-*.md` 技术合同——scenario-alignment / technical-alignment 的产出）。有对齐稿时以它为准展开调研，不重新发明需求、不推翻已拍板的口径与合同。本命令是可选环节：产出的实现计划供人评审与执行代理参考；走引擎流水线时，需求与验收以后续 prd-generate 产出的 PRD 及其派生的 prd.json 为准，计划不替代 PRD。

## 规划流程

### 阶段 1：理解功能

**深入分析功能：**

- 提炼要解决的核心问题
- 识别用户价值与业务影响
- 判断功能类型：新能力 / 增强 / 重构 / 缺陷修复
- 评估复杂度：低 / 中 / 高
- 映射会受影响的系统与组件

**创建用户故事格式，或在用户已提供用户故事时进行完善：**

```
作为一名<用户类型>
我想要<动作/目标>
以便<收益/价值>
```

### 阶段 2：收集代码库情报

**使用专门代理并进行并行分析：**

**1. 项目结构分析**

- 识别主要语言、框架与运行时版本
- 梳理目录结构与架构模式
- 确认服务 / 组件边界与集成点
- 定位配置文件（如 `pyproject.toml`、`package.json` 等）
- 找出环境初始化与构建流程

**2. 模式识别**（适合时使用专门子代理）

- 在代码库中搜索相似实现
- 识别编码约定：
  - 命名模式（CamelCase、snake_case、kebab-case）
  - 文件组织与模块结构
  - 错误处理方式
  - 日志模式与规范
- 提炼该功能所属领域的通用模式
- 记录需要避免的反模式
- 读根 `AGENTS.md`（或 `CLAUDE.md`）的硬约束与文档索引，按索引读取与本功能相关的 `docs/` 文档；monorepo 中同时读所涉子项目的 `AGENTS.md`
- `docs/golden-principles.md` 存在时无条件读取，不因功能看似简单而跳过；它是新功能立项、实现与验收的门禁，不只是背景资料

**3. 依赖分析**

- 梳理与该功能相关的外部库
- 理解这些库是如何被集成的（查看 imports、配置等）
- 按 `AGENTS.md` 文档索引查找 `docs/` 中的相关文档（如果存在）
- 记录库版本与兼容性要求

**4. 测试模式**

- 识别测试框架与测试结构（如 pytest、jest 等）
- 找到类似测试作为参考
- 理解测试组织方式（单元 / 集成）
- 记录覆盖率要求与测试规范

**5. 集成点**

- 识别需要更新的现有文件
- 确定需要创建的新文件及其位置
- 梳理路由 / API 注册模式
- 如适用，理解数据库 / 模型模式
- 如相关，识别认证 / 授权模式

**澄清歧义：**

- 如果在这一阶段需求仍不清晰，先向用户确认，再继续
- 获取具体实现偏好（库、方案、模式）
- 在继续之前先解决架构决策分歧

### 阶段 3：外部调研与文档收集

**在适合时使用专门子代理做外部调研：**

**收集文档：**

- 调研最新库版本与最佳实践
- 查找带具体锚点的官方文档
- 搜集实现示例与教程
- 识别常见坑点与已知问题
- 检查破坏性变更与迁移指南
- 记录安全注意事项（如涉及）

**整理调研引用：**

```markdown
## 相关文档

- [库官方文档](https://example.com/docs#section)
  - 具体功能实现指南
  - 原因：实现 X 功能所必需
- [框架指南](https://example.com/guide#integration)
  - 集成模式章节
  - 原因：说明如何连接组件
```

### 阶段 4：深度策略思考

**重点深入思考：**

- 这个功能如何融入现有架构？
- 关键依赖与实施顺序是什么？
- 可能出什么问题？（边界情况、竞态、错误）
- 如何进行完整测试？
- 有哪些性能影响？
- 是否存在安全考虑？
- 这种方案的可维护性如何？

**设计决策：**

- 在备选方案中进行选择，并给出清晰理由
- 不为未卜的未来预留结构（YAGNI）：可扩展性与可伸缩性只在有真实需求信号时纳入设计
- 向后兼容与迁移只在存在真实存量（数据、调用方、用户）时规划

**黄金原则门禁：**

- 逐条对照目标项目 `docs/golden-principles.md`；每条必须填写「适用 / 不适用 + 理由」「本功能设计裁决」「验证方式或证据」，不得用一句「均遵循」代替
- 对可证伪完成合同，逐条建立 `acceptanceCriteria → 验证方式/证据` 映射
- 对原生能力优先原则，核对相关 Agent/平台的当前官方能力后再做 build/adapt 裁决；不涉及 Agent 执行能力时写明不适用
- 任一适用原则尚无满足方案，或需要突破原则才能继续时，停止生成可执行计划并先交用户裁决

## 输出格式
