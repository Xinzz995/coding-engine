# /review-loop——统一质量评审入口

本命令是 `coding-x quality review` 的会话适配器，不再维护第二套评审规则。它帮助人提前发现
问题，但不能生成 GitHub 交付通过凭证，也不能代替人的产品裁决。

## 硬约束

1. 只读业务代码和文档；不得修复、暂存、提交、推送或改写需求。
2. 不采信 Builder、Validator、progress 或旧 review 的“已通过”自述。
3. 使用当前提交、当前分支 diff 和受 Git 管理的 `.coding-x/quality.json`；工作树不干净就停止。
4. Spec、工程标准、深度结构三条结果分别呈现，不重排、不互相抵消。
5. 本地输出位于 `.workspace/quality/`，明确标为反馈。共享交付记录只来自 GitHub PR 对最新
   提交生成的四项必需检查。
6. 需要产品判断、改变验收标准、删除功能或批准延期的事项保持待人裁决；本命令不替人回答。
7. 黄金原则不是自述：质量契约列出的原则来源必须逐条独立复核。计划中的“已遵循”只能定位
   意图，不能代替实现和测试证据；逐条黄金原则发现由 Standards 轴记录，等价于旧清单中的
   `` `principle:` 违反目标项目黄金原则 ``，但最终使用统一 finding schema。

## 执行

1. 确认项目根存在有效质量契约；缺失时停止并提示运行 `coding-x quality init`。
2. 确定默认分支和 merge base。当前分支与默认分支无差异时说明“无可审内容”并结束。
3. 准备五段式意图文件，内容必须来自已批准的 PRD/规格和本轮真实范围：

   - 意图
   - 验收标准
   - 非目标
   - 验证方式
   - 关联规格：逐行填写质量契约允许范围内的文件；没有独立规格时明确写
     `本 PR 意图即完整 Spec`

   如果来源缺失或相互冲突，不得自行补意图；报告 `unverifiable` 并请人补齐。
4. 意图文件放系统临时目录，不写入项目；执行：

```bash
npx coding-x quality review <claude|codex|cursor> \
  --base-ref <默认分支或明确基线> \
  --intent-file <系统临时文件> \
  --workspace .workspace
```

5. 原样呈现三条评审轴的状态和 finding。`critical/high` 必须修复；只有质量契约
   `exceptionPolicy.deferrableSeverities` 明确允许的严重度，才可能由受 Git 管理、信息完整且
   未过期的 finding 异常记录延期；`low` 仅提示。未关闭的紧急交付记录不能放行 finding。
6. 删除临时意图文件。不要把 `.workspace` 内容描述成已提交、不可伪造或可以直接合并。

## 人审输出

向人给出：

- 当前 base/head；
- Spec、工程标准、深度结构三条独立状态；
- 每条 finding 的严重度、位置、规则来源、影响和建议；
- 深度评审是否触发及原因；
- 需要人裁决的问题清单；
- 明确结尾：“这是本地反馈；修复产生新提交后必须重新运行，最终以 GitHub PR 最新提交的
  必需检查为准。”

发现问题后停在报告，不自动修改。人明确授权修复时，另行执行修复；产生任何新提交后，本轮
结果自动失效，必须从当前 head 重跑。
